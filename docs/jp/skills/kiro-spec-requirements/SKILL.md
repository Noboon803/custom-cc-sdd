# kiro-spec-requirements スキル

## 中核ミッション
- **成功基準**:
  - ステアリングのコンテキストに沿った、完全な要件ドキュメントを作成する
  - すべての受け入れ基準について、プロジェクトの EARS パターンと制約に従う
  - 実装の詳細には触れず、中核となる機能に焦点を当てる
  - スコープが誤読されるおそれがある場合は、含めるもの／含めないものの境界を明示する
  - 生成状況を追跡するためにメタデータを更新する

## 実行手順

### 手順 1: コンテキストの収集

ステアリング／仕様のコンテキストが会話の中ですでに得られている場合は、重複するファイル読み込みを省略する。
そうでない場合は、必要なコンテキストをすべて読み込む:
- 言語とメタデータのために `.kiro/specs/{feature}/spec.json` を読む
- `.kiro/specs/{feature}/brief.md` が存在すればそれを読む（ディスカバリーのコンテキスト: 課題、アプローチ、スコープの決定、境界の候補）
- プロジェクト説明のために `.kiro/specs/{feature}/requirements.md` を読む
- 中核となるステアリングのコンテキスト: `product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、機能のスコープ、ユーザーペルソナ、ビジネス／ドメインのルール、コンプライアンス／セキュリティ上の制約、運用上の制約、または既存プロダクトの境界に直接関係する場合にのみ読む
- 関連するローカルのエージェントスキルやプレイブックは、機能のホスト環境やユースケースに明確に合致し、かつユーザーが観察可能な要件を形づくるドメイン用語やワークフロールールを含む場合にのみ読む

### 手順 2: ガイドラインを読む
- EARS 構文のルールについて、このスキルのディレクトリにある `rules/ears-format.md` を読む
- 書き込み前のレビュー基準について、このスキルのディレクトリにある `rules/requirements-review-gate.md` を読む
- ドキュメント構造について、`.kiro/settings/templates/specs/requirements.md` を読む

#### 並列リサーチ（サブエージェントへのディスパッチ）

以下のリサーチ領域は互いに独立している。プロジェクトの複雑さに基づいて最適な分割方法を決める。必要に応じてサブエージェントを分割、統合、追加、または省略する。

**Agent ツールでサブエージェントに委任する**（探索内容をメインのコンテキストに持ち込まないため）:
- **コードベースからの手がかり**（既存コードベースのプロジェクト）: 要件のスコープの参考になる既存実装を探索するサブエージェントをディスパッチする。プロンプト例: "Explore this codebase for existing features related to [feature area]. Summarize: (1) what already exists, (2) relevant interfaces/APIs, (3) patterns that new requirements should align with. Return a summary under 150 lines."（訳: 「このコードベースで [機能領域] に関連する既存機能を探索せよ。(1) すでに存在するもの、(2) 関連するインターフェース／API、(3) 新しい要件が合わせるべきパターン、を要約せよ。150 行未満の要約を返せ。」）
- **ドメインリサーチ**（外部の知識が必要な場合）: WebSearch/WebFetch を使ってドメイン固有の要件、標準、ベストプラクティスを調査するサブエージェントをディスパッチする。調査結果の簡潔な要約を返させる。
- **追加のステアリングとプレイブック**: ステアリングファイルやローカルのエージェントプレイブックが多数ある場合は、それらを走査してこの機能に関連するセクションだけを返すサブエージェントをディスパッチする。

コードベースがほとんどない新規プロジェクトの場合は、サブエージェントのディスパッチを省略し、コンテキストを直接読み込む。

すべてのリサーチが完了したら、要件を生成する前に、メインのコンテキストで調査結果を統合する。

### 手順 3: 要件の下書きを生成する
- プロジェクト説明に基づいて、要件の最初の下書きを作成する
- 関連する機能を論理的な要件領域にまとめる
- すべての受け入れ基準に EARS 形式を適用する
- spec.json で指定された言語を使う
- フェーズをまたいで用語の連続性を保つ:
  - ディスカバリー = `Boundary Candidates`
  - 要件 = 必要に応じて、含めるもの／含めないものと隣接領域への期待を明示する
  - 設計 = `Boundary Commitments`
  - タスク = `_Boundary:_`
- スコープが誤読されるおそれがある場合は、実装やアーキテクチャ上の責任分担の詳細を持ち込まずに、軽量な境界のコンテキストを追加する
- レビューゲートを通過するまではこれを下書きのままにしておく。まだ `requirements.md` を書き込まない

### 手順 4: 要件の下書きをレビューする
- `rules/requirements-review-gate.md` の `Requirements Review Gate`（要件レビューゲート）を実行する
- 確定する前に、網羅性、EARS への準拠、曖昧さ、隣接領域への期待、スコープの境界をレビューする
- 問題が下書き内で完結するものであれば、要件を修正して再度レビューする
- レビューは最大 2 回の修正パスまでに制限する
- 下書きによって本当のスコープの曖昧さや矛盾が明らかになった場合は、推測で要件を書くのではなく、中断してユーザーに明確化を求める

### 手順 5: 確定とメタデータの更新
- 要件レビューゲートを通過した後にのみ、`.kiro/specs/{feature}/requirements.md` を書き込む
- `phase: "requirements-generated"` を設定する
- `approvals.requirements.generated: true` を設定する
- `updated_at` タイムスタンプを更新する

## 重要な制約

### 要件のスコープ: HOW（どうやるか）ではなく WHAT（何をするか）
要件はユーザーが観察可能な振る舞いを記述するものであり、実装を記述するものではない。何をここ（要件）に含め、何を設計に回すかを判断するのに、以下を使う:

**ユーザーに尋ねるべきこと（要件のスコープ）:**
- 機能のスコープ — 何を含め、何を含めないか
- ユーザーが観察可能な振る舞い — 「X が起きたとき、ユーザーは何を見る／体験するべきか？」
- ビジネスルールとエッジケース — 上限、エラー条件、特殊なケース
- ユーザーから見える非機能要件 — 応答時間の期待値、可用性、セキュリティレベル
- 隣接領域への期待 — ユーザーから見える振る舞いや運用者の期待を変える場合にのみ。この機能が何に依存し、何を明示的に担当しないか

**尋ねるべきでないこと（設計のスコープ — 設計フェーズに委ねる）:**
- 技術スタックの選択（データベース、フレームワーク、言語）
- アーキテクチャパターン（マイクロサービス、モノリス、イベント駆動）
- API 設計、データモデル、内部のコンポーネント構造
- 非機能要件をどう達成するか（キャッシュ戦略、スケーリングの方法）
- 設計に属する、内部の責任分担のマッピング、コンポーネントの継ぎ目、実装上の境界

**判定テスト**: EARS の受け入れ基準をいかなる技術にも言及せずに書けるなら、それは要件に属する。技術の選択が必要なら、それは設計に属する。

### その他の制約
- 各要件はテスト可能かつ曖昧さのないものでなければならない。プロジェクト説明が、スコープ、振る舞い、境界条件について複数の解釈の余地を残している場合は、その要件を生成する前にユーザーに明確化を求める。必要なだけ質問すること。自分の推測を含む要件を生成してはならない。
- EARS 文には適切な主語を選ぶ（ソフトウェアの場合はシステム名／サービス名）
- requirements.md の要件見出しには、先頭に数値の ID のみを含めなければならない（例: "Requirement 1"、"1."、"2 Feature ..."）。"Requirement A" のようなアルファベットの ID は使ってはならない。

## 出力の説明
spec.json で指定された言語で、次の内容を出力する:

1. **生成した要件の要約**: 主要な要件領域の簡潔な概要（3〜5 個の箇条書き）
2. **ドキュメントの状態**: requirements.md が更新され、spec.json のメタデータが更新されたことを確認する
3. **レビューゲート**: 要件レビューゲートを通過したことを確認する
4. **次のステップ**: どう進めるか（承認して続行するか、修正するか）をユーザーに案内する

**書式要件**:
- わかりやすさのために Markdown の見出しを使う
- ファイルパスはコードブロックに含める
- 要約は簡潔に保つ（300 語未満）

## 安全策とフォールバック

### エラーシナリオ
- **プロジェクト説明の欠落**: requirements.md にプロジェクト説明がない場合は、ユーザーに機能の詳細を尋ねる
- **テンプレートの欠落**: テンプレートファイルが存在しない場合は、警告を出したうえで、インラインのフォールバック構造を使う
- **言語が未定義**: spec.json が言語を指定していない場合は、英語（`en`）をデフォルトとする
- **要件が不完全**: 生成後、期待されるすべての機能を要件が網羅しているかを、ユーザーに明示的に尋ねる
- **ステアリングディレクトリが空**: プロジェクトのコンテキストが欠けており、要件の品質に影響する可能性があることをユーザーに警告する
- **数値でない要件見出し**: 既存の見出しに先頭の数値 ID が含まれていない場合（例えば "Requirement A" を使っている場合）、それらを数値 ID に正規化し、その対応関係を一貫して保つ（数値のラベルとアルファベットのラベルを決して混在させない）。

### 次のフェーズ: 設計の生成

**要件が承認された場合**:
- **任意のギャップ分析**（既存コードベースの場合）:
  - 実装とのギャップを分析するために `/kiro-validate-gap {feature}` を実行する
  - 既存コードベースのプロジェクトでは推奨。新規プロジェクトでは省略する
- 設計フェーズに進むために `/kiro-spec-design {feature}` を実行する
- または `/kiro-spec-design {feature} -y` で要件を自動承認し、直接先に進む

**修正が必要な場合**:
- フィードバックを伝え、`/kiro-spec-requirements {feature}` を再実行する
