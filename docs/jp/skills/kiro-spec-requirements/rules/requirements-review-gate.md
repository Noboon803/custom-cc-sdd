# 要件レビューゲート（Requirements Review Gate）

`requirements.md` を書き込む前に、要件の下書きをレビューし、下書きが通過するか、本当のスコープの曖昧さが見つかるまで、下書き内で完結する問題を修正する。

## 境界の連続性

要件を設計に変えてしまうことなく、フェーズをまたいで境界の用語を一貫して使う:

- **ディスカバリー** は `Boundary Candidates`（境界の候補）を特定する
- **要件** は、スコープが誤読されるおそれがある場合に、含めるもの、含めないもの、隣接領域への期待を明示する
- **設計** はそれらを `Boundary Commitments`（境界の確約）に変える
- **タスク** は `_Boundary:_` を使って実行可能な作業を制約する

要件は、機能の境界を、アーキテクチャ上の責任分担や実装の詳細ではなく、ユーザーや運用者が観察可能な言葉で明確にするべきである。

## スコープと網羅性のレビュー

- 下書きは、機能の中核となるユーザージャーニー、主要なスコープの境界、主なエラーケース、およびユーザーや運用者から見える意味のあるエッジ条件を網羅していなければならない。
- 機能が隣接するシステム、仕様、ワークフローに関わる場合、その区別がユーザーから見える振る舞いや運用者の期待に影響するときは、この機能がそれらに何を期待し、何を担当しないのかを下書きで明確にしなければならない。
- ユーザーから見える振る舞いを実質的に形づくるビジネス／ドメインのルール、コンプライアンス上の制約、セキュリティ／プライバシーの期待、運用上の制約は、スコープ内である場合、明示的に反映しなければならない。
- 下書きが不完全なために網羅性が欠けている場合は、下書きを修正して再度レビューする。
- プロジェクト説明やステアリングのコンテキストが曖昧、矛盾している、または規定が不十分なために、網羅性をきれいに満たせない場合は、推測するのではなく、中断してユーザーに明確化を求める。

## EARS とテスト可能性のレビュー

- すべての受け入れ基準は、`ears-format.md` で定義された EARS のルールに従わなければならない。
- すべての要件は、テスト可能かつ観察可能であり、後の設計と検証で確認できるほど具体的でなければならない。
- `requirements.md` ではなく `design.md` に属する実装の詳細は取り除く。
- 要件見出しには数値の ID のみを使わなければならない。数値のラベルとアルファベットのラベルを混在させてはならない。

## 構造と品質のレビュー

- 同じ義務を複数のセクションに重複させることなく、関連する振る舞いを一貫性のある要件領域にまとめる。
- 機能のスコープが誤読されるおそれがある場合は、含めるもの／含めないものの境界を明示する。
- 境界に関する記述は軽量かつ観察可能に保つ: コンポーネント、レイヤー、内部の責任分担を規定することなく、機能の責任と隣接領域への期待を記述する。
- 非機能の期待は、ユーザーまたは運用者が観察可能なものにとどめる。技術の選択や内部アーキテクチャの詳細は要件の外に移す。
- 「速い」「堅牢」「安全」のような曖昧な言葉は、元の資料が裏付けている限り、ユーザーから見える具体的な期待に正規化する。

## 機械的チェック

判断を適用する前に、以下を機械的に確認する:
- **数値 ID の存在**: すべての要件見出しに数値 ID（1、1.1、2 など）がある。ID のない見出しがないか下書きを走査する。
- **受け入れ基準の存在**: すべての要件に、EARS 形式の受け入れ基準が少なくとも 1 つある。"When/If/While/Where" の受け入れ文を持たない要件がないか走査する。
- **実装の言葉がない**: 要件ではなく設計に属する技術固有の用語（データベース名、フレームワーク名、API パターン）がないか走査する。見つかったものはすべてフラグを立てる。

## レビューループ

- まず機械的チェックを実行し、その後で判断に基づくレビューを行う。
- 問題が下書き内で完結するものであれば、下書きを修正してレビューゲートを再実行する。
- ループには上限を設ける: 本当の曖昧さをユーザーにエスカレーションするまでに、レビューと修正のパスは 2 回までとする。
- レビューゲートを通過した後にのみ `requirements.md` を書き込む。
