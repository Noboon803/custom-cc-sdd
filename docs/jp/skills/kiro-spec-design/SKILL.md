# kiro-spec-design スキル

## 中核ミッション
- **成功基準**:
  - すべての要件が、明確なインターフェースを持つ技術コンポーネントに対応付けられている
  - 設計が責任の境界を十分に明示しており、タスク生成とレビューの指針になる
  - 適切なアーキテクチャのディスカバリーと調査が完了している
  - 設計がステアリングのコンテキストおよび既存のパターンと整合している
  - 複雑なアーキテクチャには視覚的な図が含まれている

## 実行手順

### 手順 1: コンテキストの収集

ステアリング／仕様のコンテキストが会話からすでに得られている場合は、重複するファイル読み込みを省略する。
そうでなければ、必要なコンテキストをすべて読み込む:
- `.kiro/specs/{feature}/spec.json`、`requirements.md`、`design.md`（存在する場合）
- `.kiro/specs/{feature}/research.md`（存在する場合。`/kiro-validate-gap` によるギャップ分析を含む）
- 中核となるステアリングのコンテキスト: `product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、要件の網羅、アーキテクチャの境界、統合、実行時の前提条件、セキュリティ／パフォーマンス上の制約、または実装準備に影響するチームの規約に直接関係する場合にのみ読み込む
- ドキュメント構造として `.kiro/settings/templates/specs/design.md`
- 設計原則として、このスキルのディレクトリから `rules/design-principles.md` を読む
- ディスカバリーログの構造として `.kiro/settings/templates/specs/research.md`

**要件の承認を検証する**:
- 自動承認フラグが true の場合: spec.json 内の要件を自動承認する
- それ以外の場合: 承認状態を確認する（未承認なら停止する。「安全策とフォールバック」を参照）

### 手順 2: ディスカバリーと分析

**重要: このフェーズは、設計が完全かつ正確な情報に基づくことを保証するためのものである。**

1. **機能のタイプを分類する**:
   - **新機能**（新規）→ フルディスカバリーが必要
   - **拡張**（既存システム）→ 統合に焦点を当てたディスカバリー
   - **単純な追加**（CRUD/UI）→ 最小限のディスカバリー、またはディスカバリーなし
   - **複雑な統合** → 包括的な分析が必要

2. **適切なディスカバリープロセスを実行する**:

   **複雑な機能／新機能の場合**:
   - このスキルのディレクトリから `rules/design-discovery-full.md` を読み、実行する
   - WebSearch/WebFetch を使って徹底的な調査を行う:
     - 最新のアーキテクチャパターンとベストプラクティス
     - 外部依存関係の確認（API、ライブラリ、バージョン、互換性）
     - 公式ドキュメント、移行ガイド、既知の問題
     - パフォーマンスのベンチマークとセキュリティ上の考慮事項

   **拡張の場合**:
   - このスキルのディレクトリから `rules/design-discovery-light.md` を読み、実行する
   - 統合ポイント、既存のパターン、互換性に焦点を当てる
   - Grep を使って既存のコードベースのパターンを分析する

   **単純な追加の場合**:
   - 正式なディスカバリーは省略し、簡単なパターンチェックのみを行う

#### 並列調査（サブエージェントのディスパッチ）

以下の調査領域は互いに独立しており、Agent ツールを介して**サブエージェント**としてディスパッチできる。エージェントは機能の複雑さに基づいて最適な分割方法を判断すべきである。必要に応じてサブエージェントを分割・統合・追加・省略する。各サブエージェントは（生データではなく）**調査結果の要約**を返し、シンセシス（総合）のためにメインコンテキストをすっきり保つ。

**典型的な調査領域**（必要に応じて調整する）:
- **コードベース分析**: 既存のアーキテクチャパターン、統合ポイント、コード規約（Grep/Glob を使用）
- **外部調査**: 依存関係、API、最新のベストプラクティス（WebSearch/WebFetch を使用）
- **コンテキストの読み込み**（通常はメインコンテキストで行う）: ステアリングファイル、設計原則、ディスカバリーのルール、テンプレート

単純な追加の場合は、サブエージェントのディスパッチを完全に省略し、メインコンテキストで簡単なパターンチェックを行う。

すべての調査結果が戻ったら、先に進む前にメインコンテキストでそれらを総合する。

3. **ディスカバリーの調査結果を手順 3 のために保持する**:
   - 外部 API の契約と制約
   - 根拠を伴う技術的な決定
   - 従うべき、または拡張すべき既存のパターン
   - 統合ポイントと依存関係
   - 特定されたリスクとその緩和策
   - 境界の候補、境界外とする決定、および想定される再検証のトリガー

4. **調査結果を調査ログに永続化する**:
   - 共有テンプレートを使って `.kiro/specs/{feature}/research.md` を作成または更新する
   - ディスカバリーのスコープと主要な調査結果を要約する
   - 調査内容を、情報源とその示唆とともに記録する
   - アーキテクチャパターンの評価、設計上の決定、リスクを文書化する
   - `research.md` を作成または更新する際は、spec.json で指定された言語を使用する

### 手順 3: シンセシス（総合）

**執筆する前に、ディスカバリーの調査結果に対して設計シンセシスを適用する。**

- このスキルのディレクトリから `rules/design-synthesis.md` を読み、適用する
- このステップにはディスカバリーの調査結果の全体像が必要である。サブエージェントではなく、メインコンテキストで実行する
- シンセシスの結果（見つかった汎化、自作か採用かの決定、簡素化）を `research.md` に記録する

### 手順 4: 設計ドラフトの生成

1. **設計ドラフトを生成する**:
   - **specs/design.md テンプレートの構造と生成指示に厳密に従う**
   - **境界優先の要件**: 補助的なセクションを展開する前に、境界を明示する。ドラフトは、この仕様が何を所有し、何を所有しないか、どの依存関係が許可されるか、どのような変更が下流の再検証を必要とするかを明確に定義しなければならない。
   - **ディスカバリーの調査結果とシンセシスの結果をすべて組み込む**: 調査した情報（API、パターン、技術）とシンセシスでの決定（汎化、自作か採用か、簡素化）を、コンポーネントの定義、アーキテクチャ上の決定、統合ポイントの全体にわたって活用する
   - **File Structure Plan**（ファイル構成計画。必須）: File Structure Plan セクションを、具体的なファイルパスと責務で埋める。コードベースを分析し、どのファイルを新規作成し、どのファイルを変更する必要があるかを判断する。各ファイルは明確な責務を 1 つだけ持たなければならない。このセクションはタスクの `_Boundary:_` 注釈と実装のタスクブリーフを直接左右する。曖昧なファイル構成は、曖昧な実装を生む。
   - **Testing Strategy**（テスト戦略）: テスト項目は、汎用的なパターンからではなく、要件の受け入れ基準から導出する。各テスト項目は、この設計に含まれる具体的なコンポーネントと振る舞いを参照すべきである。E2E の経路は、要件で特定された重要なユーザーフローに対応していなければならない。「ログインが動作することをテストする」のような曖昧な記述は避け、代わりに何を確認するのか、それがなぜ重要なのかを明記する。
   - 手順 1 で既存の design.md が見つかった場合は、それを参照コンテキストとして使用する（マージモード）
   - 設計ルールを適用する: 型安全性、視覚的コミュニケーション、フォーマルな文体
   - spec.json で指定された言語を使用する
   - レビューゲートを通過するまではドラフトのままにしておき、まだ `design.md` を書き出さない

### 手順 5: 設計ドラフトのレビュー

- このスキルのディレクトリから `rules/design-review-gate.md` を読み、適用する
- 設計を確定する前に、要件の網羅性、アーキテクチャの準備状況、実装の実行可能性を確認する
- 問題がドラフト内に閉じたものであれば、設計を修正して再度レビューする
- レビューは最大 2 回の修正パスまでに制限する
- ドラフトによって要件／設計の本当のギャップが露呈した場合は、`design.md` の中で取り繕うのではなく、停止して要件の明確化に戻る

### 手順 6: 設計ドキュメントの確定

1. **最終的な設計を書き出す**:
   - 設計レビューゲートを通過した後にのみ、`.kiro/specs/{feature}/design.md` を書き出す
   - ディスカバリーの調査結果とシンセシスの結果を research.md に書き出す（まだ書き出していない場合）

2. spec.json の**メタデータを更新する**:

   - `phase: "design-generated"` を設定する
   - `approvals.design.generated: true, approved: false` を設定する
   - `approvals.requirements.approved: true` を設定する
   - `updated_at` タイムスタンプを更新する

## 重要な制約
 - **型安全性**:
   - プロジェクトの技術スタックに沿った強い型付けを徹底する。
   - 静的型付け言語では、明示的な型／インターフェースを定義し、安全でないキャストを避ける。
   - TypeScript では決して `any` を使わず、正確な型とジェネリクスを優先する。
   - 動的型付け言語では、利用可能な場合は型ヒント／アノテーション（例: Python の型ヒント）を付け、境界で入力を検証する。
   - コンポーネント間の型安全性を確保するため、公開インターフェースと契約を明確に文書化する。
- **要件のトレーサビリティ ID**: requirements.md で定義されたとおりの数値の要件 ID（例: "1.1"、"1.2"、"3.1"、"3.3"）のみを使用する。新しい ID を作り出したり、アルファベットのラベルを使ったりしてはならない。

## 出力の説明

**コマンド実行時の出力**（design.md の内容とは別物）:

spec.json で指定された言語で、簡潔な要約を提示する:

1. **ステータス**: `.kiro/specs/{feature}/design.md` に設計ドキュメントが生成されたことを確認する
2. **ディスカバリーの種別**: どのディスカバリープロセスを実行したか（full/light/minimal）
3. **主要な調査結果**: 設計を方向づけた、ディスカバリーから得た 2〜3 個の重要な洞察
4. **レビューゲート**: 設計レビューゲートを通過したことを確認する
5. **次のアクション**: 承認ワークフローの案内（「安全策とフォールバック」を参照）
6. **調査ログ**: `research.md` が最新の決定で更新されたことを確認する

**形式**: 簡潔な Markdown（200 語未満）。これはコマンドの出力であり、設計ドキュメントそのものではない

**注記**: 実際の設計ドキュメントは `.kiro/settings/templates/specs/design.md` の構造に従う。

## 安全策とフォールバック

### エラーシナリオ

**要件が未承認の場合**:
- **実行を停止する**: 承認済みの要件がなければ先に進めない
- **ユーザーへのメッセージ**: "Requirements not yet approved. Approval required before design generation."（要件はまだ承認されていない。設計の生成前に承認が必要である。）
- **推奨アクション**: "Run `/kiro-spec-design {feature} -y` to auto-approve requirements and proceed"（`/kiro-spec-design {feature} -y` を実行すれば、要件を自動承認して先に進める）

**要件が存在しない場合**:
- **実行を停止する**: 要件ドキュメントが存在しなければならない
- **ユーザーへのメッセージ**: "No requirements.md found at `.kiro/specs/{feature}/requirements.md`"（`.kiro/specs/{feature}/requirements.md` に requirements.md が見つからない）
- **推奨アクション**: "Run `/kiro-spec-requirements {feature}` to generate requirements first"（まず `/kiro-spec-requirements {feature}` を実行して要件を生成する）

**テンプレートが存在しない場合**:
- **ユーザーへのメッセージ**: "Template file missing at `.kiro/settings/templates/specs/design.md`"（`.kiro/settings/templates/specs/design.md` にテンプレートファイルが存在しない）
- **推奨アクション**: "Check repository setup or restore template file"（リポジトリのセットアップを確認するか、テンプレートファイルを復元する）
- **フォールバック**: 警告を出したうえで、インラインの基本構造を使用する

**ステアリングのコンテキストが存在しない場合**:
- **警告**: "Steering directory empty or missing - design may not align with project standards"（ステアリングのディレクトリが空か存在しない。設計がプロジェクトの標準と整合しない可能性がある）
- **続行**: 生成は続行するが、出力の中でその制約に言及する

**要件 ID が不正な場合**:
  - **実行を停止する**: requirements.md に数値の ID がない、または数値でない見出し（例: "Requirement A"）を使っている場合は、停止し、続行する前に requirements.md を修正するようユーザーに指示する。

**設計レビュー中に仕様のギャップが見つかった場合**:
- **実行を停止する**: 取り繕った `design.md` を書き出してはならない
- **ユーザーへのメッセージ**: "Design review found a real spec gap or ambiguity that must be resolved before design can be finalized."（設計レビューにより、設計を確定する前に解決しなければならない本当の仕様のギャップまたは曖昧さが見つかった。）
- **推奨アクション**: `requirements.md` を明確化または修正してから、`/kiro-spec-design {feature}` を再実行する

### 次のフェーズ: タスク生成

**設計が承認された場合**:
- **任意**: 対話的な品質レビューのために `/kiro-validate-design {feature}` を実行する
- 実装タスクを生成するために `/kiro-spec-tasks {feature}` を実行する
- または、自動承認してそのまま進めるには `/kiro-spec-tasks {feature} -y` を実行する

**修正が必要な場合**:
- フィードバックを与えて `/kiro-spec-design {feature}` を再実行する
- 既存の設計が参照として使用される（マージモード）
