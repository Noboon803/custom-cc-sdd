# 拡張のためのライトディスカバリープロセス

## 目的
機能拡張のために、既存システムと統合要件を素早く分析する。

## 焦点を絞ったディスカバリーの手順

### 1. 拡張ポイントの分析
**統合のアプローチを特定する**:
- 既存の拡張ポイントやインターフェースを見つける
- 変更のスコープ（ファイル、コンポーネント）を決める
- 従うべき既存のパターンがあるか確認する
- 後方互換性の要件を特定する

### 2. 依存関係のチェック
**互換性を確認する**:
- 新しい依存関係のバージョン互換性をチェックする
- API の契約が変わっていないことを検証する
- パイプラインに破壊的変更がないことを確かめる

### 3. 技術の簡易確認
**新しいライブラリの場合のみ**:
- WebSearch を使って公式ドキュメントを探す
- 基本的な使い方のパターンを確認する
- 既知の互換性の問題がないかチェックする
- ライセンスの互換性を確認する
- 主要な調査結果を `research.md`（技術の整合性のセクション）に記録する

### 4. 統合リスクの評価
**簡易リスクチェック**:
- 既存機能への影響
- パフォーマンスへの影響
- セキュリティ上の考慮事項
- テストの要件

## フルディスカバリーへ切り替えるべきとき
次のいずれかが見つかった場合は、フルディスカバリーに切り替える:
- 大幅なアーキテクチャ変更が必要
- 複雑な外部サービスとの統合
- セキュリティ上センシティブな実装
- パフォーマンスが極めて重要なコンポーネント
- 未知の、またはドキュメントが不十分な依存関係

## 出力要件
- 明確な統合アプローチ（境界への影響は `research.md` に記録する）
- 変更するファイル／コンポーネントの一覧
- バージョン付きの新しい依存関係
- 統合リスクとその緩和策
- テストで重点を置く領域
