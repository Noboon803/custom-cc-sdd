# 設計レビューゲート

`design.md` を書き出す前に、設計ドラフトをレビューし、設計がゲートを通過するか、本当の仕様のギャップが見つかるまで、ドラフト内に閉じた問題を修正する。

## 要件網羅性のレビュー

- `requirements.md` のすべての数値の要件 ID が設計のトレーサビリティの対応表に現れ、かつ 1 つ以上の具体的なコンポーネント、契約、フロー、データモデル、または運用上の決定によって裏付けられていなければならない。
- 外部依存関係、統合ポイント、実行時の前提条件、移行上の懸念、可観測性のニーズ、セキュリティ上の制約、またはパフォーマンス目標を持ち込むすべての要件は、`design.md` に明示的に反映されていなければならない。
- 設計ドラフトが不完全なために網羅が欠けている場合は、ドラフトを修正して再度レビューする。
- 要件が曖昧・矛盾・規定不足であるために網羅をきれいに完成できない場合は、設計の詳細をでっち上げるのではなく、停止して要件フェーズに戻る。

## アーキテクチャ準備状況のレビュー

- コンポーネントの境界は、所有者を推測せずに実装タスクを割り当てられる程度に明示されていなければならない。
- インターフェース、契約、状態遷移、統合の境界は、実装と検証が行える程度に具体的でなければならない。
- アーキテクチャに実質的な影響を与える自作か採用かの決定は `design.md` に記録しなければならない。より深い調査内容は、`research.md` がある場合はそちらに残す。
- 実行時の前提条件、移行、ロールアウト上の制約、検証フック、障害モードは、実装の順序やリスクに実質的な影響を与える場合には表に出さなければならない。

## 境界準備状況のレビュー

- 設計は、この仕様が何を所有するかを明示的に述べなければならない。
- 設計は、何が境界外であるかを明示的に述べなければならない。
- 許可される依存関係は、後でレビュー担当が境界違反を検出できる程度に具体的でなければならない。
- データ、振る舞い、または統合の責任が、明確な継ぎ目なしに複数の領域で共有されているように見える場合は、停止して設計を修正する。
- 下流の前提が「便宜上」上流のコンポーネントに埋め込まれている場合は、停止して設計を修正する。
- 境界をいくつかの直接的な箇条書きで説明できない場合、それはおそらくタスク生成にはまだ曖昧すぎる。
- 設計から、別々に動かしうる独立した責任の継ぎ目が複数あることが明らかになった場合は、それらを 1 つの仕様に無理に押し込むのではなく、停止して仕様を分割するか、ロードマップのディスカバリーに戻る。

## 実行可能性のレビュー

- 設計は、隠れた前提条件なしに、境界の定まったタスクの連なりとして実装可能でなければならない。
- アーキテクチャが並行実装を意図している箇所では、並列に進めても安全な境界が見て取れるようにすべきである。
- 投機的な抽象化を避ける: 仮定上の将来のスコープのためだけに存在するコンポーネント、アダプター、インターフェースは取り除く。
- あるセクションが、タスクから直接参照するには曖昧すぎる場合は、設計を確定する前に書き直す。

## 機械的なチェック

判断を下す前に、次の項目を機械的に確認する:
- **要件のトレーサビリティ**: `requirements.md` からすべての数値の要件 ID を抽出する。設計ドラフトを走査して各 ID を探す。設計内に見つからない ID があれば報告する。
- **境界セクションが埋まっている**: `Boundary Commitments`、`Out of Boundary`、`Allowed Dependencies`、`Revalidation Triggers` が空やプレースホルダーのみであってはならない。
- **File Structure Plan が埋まっている**: File Structure Plan（ファイル構成計画）セクションには、（"TBD" や空欄だけではなく）具体的なファイルパスが含まれていなければならない。そのセクション内にプレースホルダーのテキストがないか走査する。
- **境界 ↔ ファイル構成の整合**: File Structure Plan は、記述された責任の境界を反映していなければならない。境界セクションが主張するよりも広い所有範囲をファイル群が示唆している場合は、不一致として報告する。
- **孤立したコンポーネントがない**: 設計で言及されるすべてのコンポーネントが、ファイルパス付きで File Structure Plan に現れなければならない。対応するファイルのエントリを持たないコンポーネント名がないか走査する。

## レビューのループ

- まず機械的なチェックを行い、その後に判断に基づくレビューを行う。
- 問題がドラフト内に閉じたものであれば、ドラフトを修正してレビューゲートを再実行する。
- ループには上限を設ける: 本当の仕様のギャップとしてエスカレーションする前のレビューと修正のパスは、2 回までとする。
- `design.md` は、レビューゲートを通過した後にのみ書き出す。
