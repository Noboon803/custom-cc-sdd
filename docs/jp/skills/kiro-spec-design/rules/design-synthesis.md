# 設計シンセシス

ディスカバリーの後、設計ドキュメントを書く前に、収集した調査結果に次の 3 つのレンズを適用する。このステップには全体像が必要である。並列化してはならない。

## 1. 汎化

すべての要件をひとまとまりとして見渡す。複数の要件が、同じ根底にある問題のバリエーションになっているケースを特定する。

- 機能 A がより一般的な能力 X の特殊ケースである場合は、A を（そして将来的には B、C も）自然にサポートできるインターフェースを持つ X を設計する
- 実装のスコープは、現在の要件が求める範囲にとどめる。汎化するのはインターフェースであり、実装ではない
- 特定した汎化は、`research.md` の Design Decisions の下に記録する

## 2. 自作か採用か

形になりつつある設計の主要なコンポーネントごとに、「この問題はすでに解決されていないか」を問う。

- 要件に対応する確立された標準（RFC、プロトコル）、実績のあるライブラリ、またはプラットフォームのネイティブ機能を探す
- 大きな適合作業なしに要件に合致する場合は、独自に構築するよりも既存の解決策の採用を優先する
- 採用する場合: その解決策が活発にメンテナンスされていること、プロジェクトのスタックと互換性があること（ステアリングを確認する）、非機能要件を満たすことを確認する
- 自作する場合: 既存の解決策を却下した理由を文書化する（`research.md` に記録する）

## 3. 簡素化

形になりつつある設計のコンポーネントと抽象化レイヤーごとに、「これは必要か」を問う。

- 「念のため」や、現在の仕様にない仮定上の将来の要件のために存在するコンポーネントを取り除く
- 不要な抽象化レイヤーを平坦化する。あるインターフェースに実装が 1 つしかなく、2 つ目が見込まれない場合、その間接層は不要かもしれない
- 細かく分かれた多数のコンポーネントよりも、凝集度の高い少数のコンポーネントを優先する
- 正しい設計とは、すべての要件を満たし、かつインターフェースのレベルで拡張可能であり続ける、最小の設計である
