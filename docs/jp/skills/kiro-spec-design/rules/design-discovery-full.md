# 技術設計のためのフルディスカバリープロセス

## 目的
技術設計が完全・正確・最新の情報に基づくことを保証するため、包括的な調査と分析を行う。

## ディスカバリーの手順

### 1. 要件分析
**要件を技術的なニーズに対応付ける**
- EARS 形式からすべての機能要件を抽出する
- 非機能要件（パフォーマンス、セキュリティ、スケーラビリティ）を特定する
- 技術的な制約と依存関係を明らかにする
- 中核となる技術的課題を列挙する

### 2. 既存実装の分析
**現在のシステムを理解する**（変更／拡張する場合）:
- コードベースの構造とアーキテクチャパターンを分析する
- 再利用可能なコンポーネント、サービス、ユーティリティを洗い出す
- ドメインの境界とデータフローを特定する
- 統合ポイントと依存関係を文書化する
- アプローチを決める: 拡張するか、リファクタリングするか、ラップするか

### 3. 技術調査
**ベストプラクティスと解決策を調べる**:
- **WebSearch を使って**次を探す:
  - 類似の問題に対する最新のアーキテクチャパターン
  - その技術スタックにおける業界のベストプラクティス
  - 関連技術の最近のアップデートや変更
  - よくある落とし穴とその解決策

- **WebFetch を使って**次を分析する:
  - フレームワーク／ライブラリの公式ドキュメント
  - API リファレンスと使用例
  - 移行ガイドと破壊的変更
  - パフォーマンスのベンチマークと比較

### 4. 外部依存関係の調査
**外部サービス／ライブラリごとに**:
- 公式ドキュメントと GitHub リポジトリを探す
- API のシグネチャと認証方式を確認する
- 既存スタックとのバージョン互換性をチェックする
- レート制限と利用上の制約を調べる
- コミュニティのリソースと既知の問題を見つける
- セキュリティ上の考慮事項を文書化する
- 実装時の調査を要するギャップを記録する

### 5. アーキテクチャパターンと境界の分析
**アーキテクチャの選択肢を評価する**:
- 関連するパターン（MVC、Clean、Hexagonal、Event-driven）を比較する
- 既存アーキテクチャおよびステアリングの原則との適合性を評価する
- チーム間の衝突を避けるために必要なドメインの境界と所有の継ぎ目を特定する
- スケーラビリティへの影響と運用上の懸念を検討する
- 保守性とチームの専門知識を評価する
- 採用するパターンと却下した代替案を `research.md` に文書化する

### 6. リスク評価
**技術的リスクを特定する**:
- パフォーマンスのボトルネックとスケーリングの限界
- セキュリティの脆弱性と攻撃ベクトル
- 統合の複雑さと結合度
- 技術的負債を生むか、解消するか
- 知識のギャップとトレーニングの必要性

## 調査のガイドライン

### いつ検索するか
**常に検索する対象**:
- 外部 API のドキュメントと更新情報
- 認証／認可に関するセキュリティのベストプラクティス
- 特定したボトルネックに対するパフォーマンス最適化の手法
- 依存関係の最新バージョンと移行パス

**確信が持てない場合に検索する対象**:
- 特定のユースケースに適したアーキテクチャパターン
- データ形式／プロトコルの業界標準
- コンプライアンス要件（GDPR、HIPAA など）
- 想定される負荷に対するスケーラビリティのアプローチ

### 検索戦略
1. 公式の情報源（ドキュメント、GitHub）から始める
2. 最近のブログ記事や記事（直近 6 か月）を確認する
3. よくある問題について Stack Overflow を確認する
4. 類似のオープンソース実装を調べる

## 出力要件
設計上の決定に影響するすべての調査結果を、共有テンプレートを使って `research.md` に記録する:
- アーキテクチャ、技術の整合性、契約に影響する主要な洞察
- 調査中に判明した制約
- 推奨するアプローチと、選択したアーキテクチャパターンおよびその根拠
- 却下した代替案とトレードオフ（Design Decisions セクションに文書化する）
- Components & Interface Contracts の内容に反映させる、更新後のドメイン境界
- リスクと緩和策
- 実装時にさらなる調査が必要なギャップ
