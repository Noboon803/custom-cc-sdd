# 並列タスク分析のルール

## 目的
`tasks.md` を生成する際に、安全に並列実行できる実装タスクを特定するための一貫した方法を提供する。

## タスクの順序との関係

`(P)` の意味: このタスクは直前の同列のタスクに依存しておらず、それらと並行して実行できる。タスクの順序の原則（Task Ordering Principle。tasks-generation.md を参照）によって基盤フェーズのタスクが最初に実行されるため、中核フェーズのタスクが `(P)` の主な候補となる。

## タスクを並列とみなす場合
次の**すべて**が真である場合にのみ、タスクを並列実行可能としてマークする:

1. 保留中のタスクへの**データ依存がない**。
2. **競合するファイルや共有された可変リソース**に手を付けない。
3. 他のタスクによる**事前のレビュー／承認**を必要としない。
4. **基盤の作業が完了している**: このタスクが必要とする環境／セットアップの作業が、先行する基盤フェーズのタスクによってすでに満たされている。
5. **境界が重ならない**: `_Boundary:_` 注記によって、タスクが別々のコンポーネントに対して動作することが確認できる。

## マーキングの規約
- 条件を満たす各タスクについて、数値の識別子の直後に `(P)` を付ける。
  - 例: `- [ ] 2.1 (P) Build background worker for emails`（メール用のバックグラウンドワーカーを構築する）
- 適切な場合は、主要タスクとサブタスクの両方に `(P)` を適用する。
- 順次実行が要求された場合（例: `--sequential` フラグによって）は、`(P)` マーカーを一切付けない。
- 完了状態との混同を避けるため、`(P)` はチェックボックスの角括弧の**外側**に置く。

## まとめ方と順序のガイドライン
- 作業が同じテーマに属する場合は、並列タスクをできる限り同じ親の下にまとめる。
- 明らかな前提条件や注意点は、詳細の箇条書きに列挙する（例: 「1.2 のスキーママイグレーションが必要」）。
- 2 つのタスクが似て見えても並列に実行して安全でない場合は、ブロックしている依存関係を明示的に指摘する。
- 入れ物でしかない主要タスク（自身の実行可能な詳細の箇条書きを持たないもの）には `(P)` を付けない — 並列実行はサブタスクの階層で評価する。

## 品質チェックリスト
タスクに `(P)` を付ける前に、次を満たしていることを確認する:

- このタスクを並行して実行しても、マージやデプロイの競合が生じないことを検証した。
- `_Boundary:_` 注記が、コンポーネントのスコープが重ならないことを示していると確認した。
- 共有状態に関する前提を、詳細の箇条書きに記載した。
- 実装を独立してテストできることを確認した。
- この `(P)` タスクが、別の主要タスクグループにある特定の先行作業をなお必要とする場合は、`_Depends: X.X_` を追加した。

いずれかのチェックが満たされない場合は、タスクに `(P)` を**付けてはならず**、タスクの詳細にその依存関係を説明する。
