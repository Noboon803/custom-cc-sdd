# タスク生成のルール

## 中核となる原則

### 1. 自然言語による記述
コードの構造ではなく、実現する能力と成果に焦点を当てる。

**記述するもの**:
- 実現すべき機能
- ビジネスロジックと振る舞い
- 機能と能力
- ドメインの言葉と概念
- データの関係とワークフロー

**避けるもの**:
- ファイルパスとディレクトリ構造
- 関数／メソッドの名前とシグネチャ
- 型定義とインターフェース
- クラス名と API コントラクト
- 具体的なデータ構造

**根拠**: 実装の詳細（ファイル、メソッド、型）は design.md で定義される。タスクは、行うべき機能的な作業を記述する。

### 2. タスクの順序の原則（Task Ordering Principle）

**順序は依存関係を意味する**: タスク N は、それより前のすべてのタスクに暗黙的に依存する。これが主要な依存関係の仕組みである。

**タスクは次のフェーズ順に従わなければならない**:
1. **基盤（Foundation）**: 環境のセットアップ、テスト基盤、共有ユーティリティ、データベーススキーマ、設定
2. **中核（Core）**: 主要な機能の実装（並列実行可能なタスクはここにまとめる）
3. **統合（Integration）**: コンポーネント同士の接続、境界をまたぐ接続
4. **検証（Validation）**: E2E テスト、エッジケース、リグレッションのチェック

**根拠**: 基盤の作業は他のすべての作業のブロックを解除する。セットアップタスクを早い段階に置くことで、後続の作業がブロックされるのを防ぐ。基盤がすでに完了しているため、中核のタスクは多くの場合並列に実行できる。

### 3. タスクの統合と進行

**すべてのタスクは次を満たさなければならない**:
- 前の成果物の上に積み上げる（孤立したコードがない）
- システム全体につながる（宙に浮いた機能がない）
- 段階的に進める（複雑さが大きく跳ね上がらない）
- design.md で定義されたアーキテクチャの境界（Architecture Pattern & Boundary Map）を尊重する
- design.md に記載されたインターフェースのコントラクトを守る
- 主要タスクの要約は控えめに使う — 作業が子タスクで完全に表現されている場合は、詳細の箇条書きを省略する。

**最後は統合タスクで締めくくり**、すべてを接続する。

### 4. 依存関係の宣言

**デフォルト**: ほとんどの依存関係は、順番に並べることで処理される（タスク N はそれより前のタスクに依存する）。

**明示的な宣言が必要な場合**:
- タスクが、別の主要タスクグループにある特定のタスクに依存する場合（境界をまたぐ）
- 順序だけでは依存関係が自明でない場合
- タスクが自分の位置より先に進められる（`(P)` で宣言される）が、それでも特定の先行作業を必要とする場合

**書式**: `_Depends: 1.2, 2.3_` — タスクの詳細セクション内で `_Requirements:_` と並べて置く。

**注記を付けすぎない**: タスクが直前のタスクに依存しているだけであれば、順序だけで十分である。

### 5. 境界のスコープ

**各タスクは、design.md のコンポーネント名／モジュール名を使って、自身のコンポーネント境界を宣言するべきである**:
- `_Boundary: AuthService_` または `_Boundary: API Layer, UserRepository_`
- 並列の安全性の検証に役立つ: 境界が重ならないタスクは並列の候補となる
- エージェントがスコープを理解するのに役立つ: 何に手を付け、何に手を付けないか

**使うべき場面**: `(P)` が付いたタスクでは、並列の安全性を検証するために必須である。記述からスコープが明らかな順次実行のタスクでは省略する。

**境界のルール**:
- 実行可能な各タスクは、単一の責任境界の中にとどめるべきである
- 作業がどうしても境界をまたぐ場合は、通常の実装タスクではなく、明示的な統合タスクにする
- 局所的に見えるタスクの中に、境界をまたぐ調整を隠してはならない

### 6. 柔軟なタスクサイズ

**ガイドライン**:
- **主要タスク**: 論理的に必要なだけのサブタスクを持つ（凝集度でまとめる）
- **サブタスク**: それぞれ 1〜3 時間、サブタスクあたり 3〜10 個の詳細
- 細かすぎず、大雑把すぎないバランスを取る

**恣意的な数を強制しない** — 論理的なまとまりによって構造を決める。

### 7. 要件の対応付け

**各タスクの詳細セクションの末尾に次を置く**:
- `_Requirements: X.X, Y.Y_` として、**数値の要件 ID のみ**を（カンマ区切りで）列挙する。説明文、括弧、翻訳、自由形式のラベルを決して付け加えない。
- 横断的な要件については、関連するすべての要件 ID を列挙する。requirements.md のすべての要件は数値 ID を持っていなければならない。ID が欠けている場合は、タスクを生成する前に中断して requirements.md を修正する。
- 役に立つ場合は、design.md のコンポーネント／インターフェースを参照する（例: `_Contracts: AuthService API`）

### 7.5 観察可能な完了

**実行可能な各タスクには、観察可能な完了状態を記述する詳細の箇条書きを少なくとも 1 つ含めなければならない**:
- 成果物、実行時の振る舞い、永続化された状態、UI の状態、エンドポイントの振る舞い、テスト結果、または統合の結果として表現する
- 「サポートを実装する」「つなぎ込む」「ロジックを処理する」のような曖昧な箇条書きは、具体的で観察可能な結果と組み合わせない限り避ける
- 詳細の箇条書きのうち 1 つが、「このタスクが完了したとき、何が真になっているか？」に明確に答えるようにするのが望ましい
- これは既存のタスク本文の中に収める。追加の管理用フィールドを加えてはならない

### 8. コードのみに焦点を当てる

**含めるのは次のみ**:
- コーディングタスク（実装）
- テストタスク（単体、統合、E2E）
- 技術的なセットアップタスク（インフラ、設定）

**除外するもの**:
- デプロイのタスク
- ドキュメント作成のタスク
- ユーザーテスト
- マーケティング／ビジネス活動

## タスク計画レビューゲート（Task Plan Review Gate）

`tasks.md` を書き込む前に、タスク計画の下書きをレビューし、計画が通過するか、本当の仕様のギャップが見つかるまで、計画内で完結する問題を修正する。

### 網羅性のレビュー

- `requirements.md` のすべての要件 ID が、少なくとも 1 つのタスクに現れていなければならない。
- `design.md` のすべての設計コンポーネント、インターフェース／コントラクト、統合ポイント、実行時の前提条件、検証上の関心事が、少なくとも 1 つのタスクに反映されていなければならない。
- タスク計画が不完全なために網羅性が欠けている場合は、タスクの下書きを修正して再度レビューする。
- 要件や設計が曖昧、矛盾している、または規定が不十分なために網羅性をきれいに追加できない場合は、`tasks.md` でギャップを取り繕うのではなく、中断して要件／設計のフェーズに戻る。

### 実行可能性のレビュー

- すべてのサブタスクは、書かれたとおりに実行可能でなければならず、通常は 1〜3 時間以内に収まる。
- すべてのサブタスクは、確認可能な成果物（振る舞い、成果物、エンドポイント、UI の状態、設定、マイグレーション、テスト、または統合の結果）を生み出さなければならない。
- 実行可能なすべてのサブタスクには、観察可能な完了条件を述べる詳細の箇条書きが少なくとも 1 つ含まれていなければならない。
- 独立して確認可能な複数の成果を組み合わせているタスクは分割する。
- 複数の責任境界を組み合わせているタスクは、明示的な統合タスクでない限り分割する。
- 多くのタスクが広い `_Boundary:_` スコープや、繰り返しの境界をまたぐ調整を必要とする場合は、無理にタスク生成を押し通すのではなく、中断して設計またはロードマップの分解に戻る。
- 小さすぎるタスク、管理作業だけのタスク、意味のある実行単位になっていないタスクは、統合するかまとめる。
- 暗黙の前提条件は、先行するタスクとして明示する。
- 編集後に `_Depends:_`、`_Boundary:_`、`(P)` マーカーを再確認し、並行性の主張が引き続き設計の境界および依存グラフと一致するようにする。

### レビューループ

- `tasks.md` を書き込む前に、タスク計画の下書きに対してレビューゲートを実行する。
- 問題がタスク計画内で完結するものであれば、下書きを修正してレビューゲートを再実行する。
- ループには上限を設ける: 本当の仕様のギャップをエスカレーションするまでに、レビューと修正のパスは 2 回までとする。
- レビューゲートを通過した後にのみ `tasks.md` を書き込む。

### 任意のテストカバレッジタスク

- 設計がすでに機能面の網羅を保証しており、MVP の迅速な提供が優先される場合は、純粋にテスト目的の後続作業（例: 基本的なレンダリング／単体テスト）を、`- [ ]*` のチェックボックス形式を使って**任意**としてマークする。
- 任意マーカーは、サブタスクがその詳細の箇条書きの中で requirements.md の受け入れ基準を直接参照している場合にのみ付ける。
- 実装作業や、統合にとって重要な確認を任意としてマークしてはならない — `*` は、MVP 後に改めて対応できる、補助的／延期可能なテストカバレッジのためだけに使う。

## タスク階層のルール

### 最大 2 階層
- **第 1 階層**: 主要タスク（1、2、3、4...）
- **第 2 階層**: サブタスク（1.1、1.2、2.1、2.2...）
- **それより深い入れ子にしない**（1.1.1 は不可）
- 主要タスクが実行可能な項目を 1 つしか含まない場合は、構造をまとめて、そのサブタスクを主要タスクの階層に昇格させる（例: `1.1` を `1.` に置き換える）。
- 主要タスクが単なる入れ物として存在する場合は、チェックボックスの説明を簡潔に保ち、詳細の箇条書きの重複を避ける — 具体的な内容はサブタスクに残す。

### 連番
- 主要タスクは必ず 1、2、3、4、5... と増やしていかなければならない
- サブタスクは主要タスクごとにリセットする: 1.1、1.2、次に 2.1、2.2...
- 主要タスクの番号を決して繰り返さない

### 並列分析（デフォルト）
- 明示的に無効化されない限り（例: `--sequential` フラグ）、並列分析は有効であるとみなす。
- `(P)` の意味: このタスクは直前の同列のタスクに依存しておらず、それらと並行して実行できる。
- **すべての**条件が成り立つ場合に、並行して実行できるタスクを特定する:
  - 保留中の他のタスクへのデータ依存がない
  - ファイルやリソースの共有による競合がない
  - 他のタスクによる事前のレビュー／承認を必要としない
  - `_Boundary:_` 注記によって、コンポーネントのスコープが重ならないことが確認できる
- 基盤フェーズのタスク（「タスクの順序の原則」を参照）が `(P)` になることはまれである — それらは共有の前提条件を確立するものだからである。
- 中核フェーズのタスクは、基盤がすでに完了しているため、`(P)` の主な候補となる。
- 特定した並列タスクが、Architecture Pattern & Boundary Map で定義された別々の境界の中で動作することを検証する。
- design.md の API／イベントのコントラクトが、競合を引き起こすような形で重なっていないことを確認する。
- 境界をまたぐ依存関係を持つ `(P)` タスクは、`_Depends: X.X_` を明示的に宣言しなければならない。
- 並列実行可能な各タスクについて、タスク番号の直後に `(P)` を付ける:
  - 例: `- [ ] 2.1 (P) Build background worker`（バックグラウンドワーカーを構築する）
  - 適切な場合は、主要タスクとサブタスクの両方に適用する。
- sequential モードが要求された場合は、`(P)` マーカーを一切付けない。
- 並列タスクは論理的にまとめ（可能であれば同じ親の下に）、順序に関する注意点があれば詳細の箇条書きで強調する。
- タスクが似て見える場合でも、`(P)` を妨げる依存関係は明示的に指摘する。

### チェックボックスの書式
```markdown
- [ ] 1. 基盤: 環境とテスト基盤のセットアップ
- [ ] 1.1 サブタスクの説明
  - 詳細項目 1
  - 詳細項目 2
  - 観察可能な完了条件
  - _Requirements: X.X_

- [ ] 2. 中核機能 A
- [ ] 2.1 (P) サブタスクの説明
  - 詳細項目...
  - 観察可能な完了条件
  - _Requirements: Y.Y_
  - _Boundary: AuthService_

- [ ] 2.2 (P) サブタスクの説明
  - 詳細項目...
  - 観察可能な完了条件
  - _Requirements: Z.Z_
  - _Boundary: UserRepository_

- [ ] 3. 統合と接続
- [ ] 3.1 サブタスクの説明
  - 詳細項目...
  - 観察可能な完了条件
  - _Depends: 2.1, 2.2_
  - _Requirements: W.W_
```

## 要件の網羅

**必須のチェック**:
- requirements.md のすべての要件を必ず網羅しなければならない
- すべての要件 ID をタスクの対応付けと照合する
- ギャップが見つかった場合: 要件フェーズまたは設計フェーズに戻る
- 対応するタスクのないまま残される要件があってはならない

`N.M` 形式の数値の要件 ID を使う。`N` は requirements.md の最上位の要件番号（例: Requirement 1 → 1.1、1.2、Requirement 2 → 2.1、2.2）、`M` はその要件グループ内のローカルな連番である。

意図的に先送りした要件があれば、その根拠とともに記録する。
