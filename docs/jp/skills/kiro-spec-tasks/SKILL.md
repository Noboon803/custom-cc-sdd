# kiro-spec-tasks スキル

## 中核ミッション
- **成功基準**:
  - すべての要件が具体的なタスクに対応付けられている
  - タスクの大きさが適切である（それぞれ 1〜3 時間）
  - 適切な階層を持ち、タスクの進行が明確である
  - 実現する能力に焦点を当てた自然言語の記述になっている
  - `tasks.md` を書き込む前に、軽量なタスク計画の健全性レビューによって、タスクグラフが実行可能であることが確認されている

## 実行手順

### 手順 1: コンテキストの収集

ステアリング／仕様のコンテキストが会話の中ですでに得られている場合は、重複するファイル読み込みを省略する。
そうでない場合は、必要なコンテキストをすべて読み込む:
- `.kiro/specs/{feature}/spec.json`、`requirements.md`、`design.md`
- `.kiro/specs/{feature}/tasks.md`（存在する場合。マージモードのため）
- 中核となるステアリングのコンテキスト: `product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、要件の網羅性、設計の境界、実行時の前提条件、またはタスクの実行可能性に影響するチームの規約に直接関係する場合にのみ読む

- 実行モードを決定する:
  - `sequential = (sequential flag is true)`（sequential フラグが true なら sequential）

**承認の検証**:
- 自動承認フラグ（`-y`）が true の場合: spec.json で要件と設計を自動承認する。タスクの承認も手順 4 で自動的に処理される。
- そうでない場合: 両方が承認済みであることを確認する（承認されていなければ中断する。「安全策とフォールバック」を参照）

### 手順 2: 実装タスクの生成

- 原則について、このスキルのディレクトリにある `rules/tasks-generation.md` を読む
- 並列の判断基準について、このスキルのディレクトリにある `rules/tasks-parallel-analysis.md` を読む
- 書式について、`.kiro/settings/templates/specs/tasks.md` を読む（`(P)` マーカーに対応している）

#### 並列リサーチ

以下のリサーチ領域は互いに独立しており、並列に実行できる:
1. **コンテキストの読み込み**: 仕様ドキュメント（requirements.md、design.md）、ステアリングファイル
2. **ルールの読み込み**: tasks-generation.md、tasks-parallel-analysis.md、タスクのテンプレート

すべての並列リサーチが完了したら、タスクを生成する前に調査結果を統合する。

**すべてのルールに従ってタスクリストを生成する**:
- spec.json で指定された言語を使う
- すべての要件をタスクに対応付け、数値の要件 ID のみを（カンマ区切りで）列挙する。説明的な接尾辞、括弧、翻訳、自由形式のラベルは付けない
- すべての設計コンポーネントが含まれていることを確認する
- タスクの進行が論理的かつ段階的であることを確認する
- 実行可能な各サブタスクに、「完了」がどういう状態かを観察可能な言葉で述べる詳細の箇条書きが少なくとも 1 つ含まれていることを確認する
- 通常の実装タスクは単一の責任境界の中にとどめる。作業が境界をまたぐ場合は、明示的な統合タスクにする
- `!sequential` の場合、並列の基準を満たすタスクに `(P)` マーカーを付ける
- 並列に見えても安全ではないタスクについては、`(P)` を妨げている依存関係を明記する
- sequential モードが true の場合は、`(P)` を一切付けない
- 既存の tasks.md が見つかった場合は、新しい内容とマージする

### 手順 3: タスク計画のレビュー

- タスク計画の下書きは作業メモリ内に保持する。まだ `tasks.md` を書き込んではならない
- `rules/tasks-generation.md` の `Task Plan Review Gate`（タスク計画レビューゲート）を実行する
- 網羅性をレビューする:
  - すべての要件 ID が少なくとも 1 つのタスクに現れている
  - すべての設計コンポーネント、コントラクト、統合ポイント、実行時の前提条件、検証上の関心事が反映されている
- 実行可能性をレビューする:
  - 各サブタスクが、実行可能な 1〜3 時間の作業単位である
  - 各サブタスクに、確認可能な成果物がある
  - 実行可能な各サブタスクに、観察可能な完了を示す箇条書きが含まれている
  - 暗黙の前提条件が隠れたまま残っていない
  - `_Depends:_`、`_Boundary:_`、`(P)` マーカーが、依存グラフおよびアーキテクチャの境界と引き続き一致している
- 問題がタスク計画内で完結するものであれば、書き込む前に下書きを修正してレビューゲートを再実行する
- レビューは最大 2 回の修正パスまでに制限する
- レビューによって要件／設計の本当のギャップや矛盾が明らかになった場合は、穴埋めのタスクをでっち上げるのではなく、中断してユーザーを要件／設計に差し戻す

### 手順 3.5: タスクグラフの健全性レビューの実行

`tasks.md` を書き込む前に、タスクグラフについて軽量で独立した健全性レビューを 1 回実行する。

- 新しいサブエージェントをディスパッチできる場合は、この手順のために新しいレビュー用サブエージェントを 1 つ起動する。そうでない場合は、同じレビューを現在のコンテキストで実施する。
- 渡すのは、ファイルパス、タスク計画の下書き、および既存の `tasks.md` を更新する場合はマージのコンテキストのみとする。レビュー担当は、親がまとめた網羅性の要約に頼るのではなく、`requirements.md`、`design.md`、タスク生成ルールを直接読むべきである。
- 以下のみをチェックする:
  - 隠れた前提条件、または欠けているセットアップタスク
  - 依存関係や順序の誤り
  - タスク間の境界の重複や、責任分担の曖昧さ
  - 大きすぎる、曖昧すぎる、明示的な統合タスクでないのに境界をまたいでいる、または確認可能な成果物が欠けているタスク
  - 要件、設計、タスクグラフの間に持ち込まれた矛盾
- 判定を 1 つ返す:
  - `PASS`
  - `NEEDS_FIXES`
  - `RETURN_TO_DESIGN`
- `NEEDS_FIXES` の場合は、下書きを 1 回修正し、健全性レビューを 1 回だけ再実行する。
- `RETURN_TO_DESIGN` の場合は、`tasks.md` を書き込まずに中断し、要件／設計の中の正確なギャップを指し示す。
- これには上限を設ける。2 回目の完全な計画サイクルにしてはならない。

### 手順 4: 確定

**tasks.md を書き込む**:
- `.kiro/specs/{feature}/tasks.md` を作成／更新する
- spec.json のメタデータを更新する:
  - `phase: "tasks-generated"` を設定する
  - `approvals.tasks.generated: true, approved: false` を設定する
  - `approvals.requirements.approved: true` を設定する
  - `approvals.design.approved: true` を設定する
  - `updated_at` タイムスタンプを更新する

**承認**:
- 自動承認フラグ（`-y`）が true の場合:
  - spec.json で `approvals.tasks.approved: true` を設定する
  - タスクの要約（タスク数、主要なグループ、並列マーカー）を表示する
  - 次のように応答する: "Tasks generated and auto-approved. Start implementation with `/kiro-impl {feature}`"（タスクを生成し、自動承認した。`/kiro-impl {feature}` で実装を開始せよ）
- そうでない場合（対話モード）:
  - 生成したタスクの要約（タスク数、主要なグループ、並列マーカー）を表示する
  - ユーザーに次のように尋ねる: "Tasks generated. Approve and proceed to implementation?"（タスクを生成した。承認して実装に進むか？）
  - ユーザーが承認した場合:
    - spec.json で `approvals.tasks.approved: true` を設定する
    - 次のように応答する: "Tasks approved. Start implementation with `/kiro-impl {feature}`"（タスクが承認された。`/kiro-impl {feature}` で実装を開始せよ）
  - ユーザーが変更を望む場合:
    - `approvals.tasks.approved: false` のままにする
    - 何を調整して再実行すればよいかの案内を添えて応答する

## 重要な制約
- **タスクの統合**: すべてのタスクはシステムにつながっていなければならない（孤立した作業がない）
- **境界の注記**: `(P)` タスクでは必須、すべてのタスクで推奨（`_Boundary: ComponentName_`）
- **明示的な依存関係**: 境界をまたぐ、自明でない依存関係は `_Depends: X.X_` で宣言する
- **実行可能な成果物の粒度**: 各タスクは確認可能な成果物（ファイル、エンドポイント、UI コンポーネント、設定）を生み出さなければならない。インフラのタスク（プロジェクトの雛形作成、マニフェスト、ホストとの統合、ビルド設定）は明示しなければならない — それらが存在すると決して仮定しない
- **観察可能な完了状態**: 実行可能な各サブタスクには、新たな管理用フィールドを追加することなく、完了した状態を見える形にする詳細の箇条書きを少なくとも 1 つ含めなければならない
- **暗黙の前提条件の禁止**: タスクがランタイム、SDK、フレームワークのセットアップ、または設定ファイルを必要とする場合、そのセットアップは先行する別のタスクにしなければならない

## 出力の説明

spec.json で指定された言語で、簡潔な要約を出力する:

1. **状態**: `.kiro/specs/{feature}/tasks.md` にタスクが生成されたことを確認する
2. **タスクの要約**:
   - 合計: 主要タスク X 個、サブタスク Y 個
   - Z 個すべての要件を網羅
   - 平均タスクサイズ: サブタスクあたり 1〜3 時間
3. **品質の検証**:
   - すべての要件がタスクに対応付けられている
   - 設計の網羅性と実行時の前提条件をレビュー済み
   - タスクの依存関係を確認済み
   - タスク計画レビューゲートを通過
   - 独立したタスクグラフの健全性レビューを通過
   - テストタスクを含む
4. **次のアクション**: タスクをレビューし、準備ができたら先に進む

**書式**: 簡潔に（200 語未満）

## 安全策とフォールバック

### エラーシナリオ

**要件または設計が承認されていない**:
- **実行を中断する**: 承認済みの要件と設計がなければ先に進めない
- **ユーザーへのメッセージ**: "Requirements and design must be approved before task generation"（タスク生成の前に、要件と設計が承認されていなければならない）
- **推奨アクション**: "Run `/kiro-spec-tasks {feature} -y` to auto-approve all (requirements, design, and tasks) and proceed"（`/kiro-spec-tasks {feature} -y` を実行すると、すべて（要件、設計、タスク）を自動承認して先に進む）

**要件または設計の欠落**:
- **実行を中断する**: 両方のドキュメントが存在しなければならない
- **ユーザーへのメッセージ**: "Missing requirements.md or design.md at `.kiro/specs/{feature}/`"（`.kiro/specs/{feature}/` に requirements.md または design.md がない）
- **推奨アクション**: "Complete requirements and design phases first"（先に要件フェーズと設計フェーズを完了せよ）

**要件の網羅が不完全**:
- **警告**: "Not all requirements mapped to tasks. Review coverage."（すべての要件がタスクに対応付けられていない。網羅性をレビューせよ）
- **ユーザーの対応が必要**: 意図的なギャップであることを確認するか、タスクを再生成する

**タスクのレビュー中に仕様のギャップが見つかった**:
- **実行を中断する**: 取り繕った `tasks.md` を書き込んではならない
- **ユーザーへのメッセージ**: "Requirements/design do not provide enough clear coverage to generate an executable task plan"（要件／設計が、実行可能なタスク計画を生成できるほど明確な網羅性を備えていない）
- **推奨アクション**: "Refine requirements.md or design.md, then re-run `/kiro-spec-tasks {feature}`"（requirements.md または design.md を改善してから、`/kiro-spec-tasks {feature}` を再実行せよ）

**テンプレート／ルールの欠落**:
- **ユーザーへのメッセージ**: "Template or rules files missing in `.kiro/settings/`"（`.kiro/settings/` にテンプレートまたはルールファイルがない）
- **フォールバック**: 警告を出したうえで、インラインの基本構造を使う
- **推奨アクション**: "Check repository setup or restore template files"（リポジトリのセットアップを確認するか、テンプレートファイルを復元せよ）
- **数値の要件 ID の欠落**:
  - **実行を中断する**: requirements.md のすべての要件は数値 ID を持っていなければならない。数値 ID を持たない要件が 1 つでもある場合は、中断し、タスクを生成する前に requirements.md を修正するよう求める。

### 次のフェーズ: 実装

タスクは手順 4 でユーザーの確認を経て承認される。承認されたら:
- 自律的な実装: `/kiro-impl {feature}`
- 特定のタスクのみ: `/kiro-impl {feature} 1.1,1.2`
