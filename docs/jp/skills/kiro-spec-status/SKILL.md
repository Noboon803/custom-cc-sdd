# kiro-spec-status スキル

## 中核ミッション
- **成功基準**:
  - 現在のフェーズと完了状況を示す
  - 次のアクションとブロック要因を特定する
  - 進捗を明確に見える化する
  - 利用可能な場合は、境界の準備状況、上流／下流のコンテキスト、再検証が必要になりそうな箇所を提示する

## 実行手順

### 手順 1: 仕様のコンテキストの読み込み
- メタデータとフェーズの状態について、`.kiro/specs/$ARGUMENTS/spec.json` を読む
- `.kiro/specs/$ARGUMENTS/brief.md` が存在すればそれを読む
- 既存のファイルを読む: `requirements.md`、`design.md`、`tasks.md`（存在する場合）
- 利用可能なファイルについて、`.kiro/specs/$ARGUMENTS/` ディレクトリを確認する
- `.kiro/steering/roadmap.md` が存在し、この仕様がその中に登場する場合は、それを読む

### 手順 2: 状態の分析

**各フェーズを解析する**:
- **要件**: 要件と受け入れ基準の数を数える
- **設計**: アーキテクチャ、コンポーネント、図の有無と、境界のセクションが存在するかを確認する
- **タスク**: 完了したタスク数と全タスク数を数える（`- [x]` と `- [ ]` を解析する）
- **承認**: spec.json の承認状態を確認する
- **境界のコンテキスト**:
  - brief.md から: `Boundary Candidates`、`Upstream / Downstream`、`Existing Spec Touchpoints` が存在すれば記録する
  - design.md から: `Boundary Commitments`、`Out of Boundary`、`Allowed Dependencies`、`Revalidation Triggers` が存在すれば記録する
  - roadmap.md から: 上流の依存関係と、この仕様が `Existing Spec Updates` に隣接しているかどうかを記録する
- **再検証ウォッチリスト**:
  - この仕様が変更された場合に再検証が必要になりうる、下流の仕様、隣接する既存仕様の更新、またはロールアウトに影響しやすい設計上のメモを特定する
  - 現在の仕様の形が広すぎるように見え、局所的な修正を重ねるよりもロードマップ／設計の分割が望ましい可能性がある場合は、それを指摘する

### 手順 3: レポートの生成

spec.json で指定された言語で、次の内容を網羅するレポートを作成する:
1. **現在のフェーズと進捗**: 仕様がワークフローのどこにあるか
2. **完了状況**: 各フェーズの完了率
3. **タスクの内訳**: タスクが存在する場合は、完了数／残り数を示す
4. **境界のコンテキスト**: 利用可能な場合は、上流／下流、境界外、許可された依存関係に関するメモ
5. **再検証ウォッチリスト**: この仕様の変更によって影響を受けそうな、下流または隣接する作業
6. **次のアクション**: 次に何を行う必要があるか
7. **ブロック要因**: 進捗を妨げている問題

**書式**: 状態を示す絵文字を使った、明確で一覧しやすい書式

## 安全策とフォールバック

### エラーシナリオ

**仕様が見つからない**:
- **メッセージ**: "No spec found for `$ARGUMENTS`. Check available specs in `.kiro/specs/`"（`$ARGUMENTS` の仕様が見つからない。`.kiro/specs/` にある利用可能な仕様を確認せよ）
- **アクション**: 利用可能な仕様ディレクトリを一覧表示する

**不完全な仕様**:
- **警告**: どのファイルが欠けているかを特定する
- **推奨アクション**: 次のフェーズのコマンドを示す

### すべての仕様の一覧表示

利用可能なすべての仕様を確認するには:
- 引数なしで実行するか、ワイルドカードを使う
- `.kiro/specs/` にあるすべての仕様を、その状態とともに表示する
