# kiro-validate-impl スキル

## 役割
個々のタスクは、実装中にタスクごとのレビュー担当によって既にレビューされている。あなたの仕事は、すべてのタスクをまとめて見たときに初めて見えてくる問題を捕捉することである。

境界に関する用語の連続性:
- ディスカバリーは `Boundary Candidates`（境界候補）を特定する
- 設計は `Boundary Commitments`（境界の確約）を確定する
- タスクは `_Boundary:_` で実行を制約する
- 機能の検証は、タスク横断の `Boundary Violations`（境界違反）を確認する

## コアミッション
- **成功基準**:
  - tasks.md のすべてのタスクが `[x]` になっている
  - テストスイート全体がパスする（タスクごとのテストだけではない）
  - タスク横断の統合が機能する（コンポーネント間でデータが流れ、インターフェースが一致する）
  - 要件のカバレッジがすべてのタスクを通じて完全である（タスク間の隙間がない）
  - 設計の構造がエンドツーエンドで反映されている（コンポーネント単位だけではない）
  - 孤立したコード、競合する実装、統合の継ぎ目の問題、境界のはみ出しがない

## このスキルが行わないこと
タスクごとの確認は、`/kiro-impl` 中のレビュー担当の責任である。このスキルは以下を再確認**しない**:
- 個々のタスクの受け入れ基準
- ファイルごとの実在性チェック（モック／スタブの検出）
- 単一タスクの仕様との整合

このスキルの主な問いは次のとおりである: 完了したタスクをまとめて見たとき、それらは設計された境界の継ぎ目と依存方向を依然として守っているか。

## 実行ステップ

### ステップ 1: 検証対象の検出

**引数が指定されていない場合**:
- 会話履歴から `/kiro-impl` コマンドを解析し、最近実装された機能とタスクを検出する
- `.kiro/specs/` をスキャンし、完了済みタスク `[x]` を持つ機能を探す
- 検出した実装を報告する（例: "user-auth: 1.1, 1.2, 1.3"）

**機能が指定された場合**（機能は指定、タスクは空）:
- 指定された機能を使う
- `.kiro/specs/{feature}/tasks.md` 内のすべての完了済みタスク `[x]` を検出する

**機能とタスクの両方が指定された場合**（明示モード）:
- 指定された機能とタスクのみを検証する（例: `user-auth 1.1,1.2`）

### ステップ 2: コンテキストの収集

ステアリング／仕様のコンテキストが会話から既に得られている場合は、冗長なファイル読み込みをスキップする。
そうでない場合は、検出した各機能について:
- メタデータのために `.kiro/specs/<feature>/spec.json` を読む
- 要件のために `.kiro/specs/<feature>/requirements.md` を読む
- 設計の構造のために `.kiro/specs/<feature>/design.md` を読む
- タスクリストと実装メモ（Implementation Notes）のために `.kiro/specs/<feature>/tasks.md` を読む
- 中核のステアリングコンテキスト: `product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、検証対象の境界、実行時の前提条件、統合、ドメインルール、セキュリティ／パフォーマンスの制約、または GO/NO-GO の判断に影響するチームの規約に直接関係する場合にのみ読む

**正規の検証コマンドを見つける**:
- リポジトリ内の信頼できる情報源を次の順で調べる: プロジェクトのスクリプト／マニフェスト（`package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、アプリのマニフェスト）、タスクランナー（`Makefile`、`justfile`）、CI／ワークフローファイル、既存の e2e／統合テストの設定、最後に `README*`
- このリポジトリ向けの機能レベルの検証セットを導き出す: `TEST_COMMANDS`、`BUILD_COMMANDS`、`SMOKE_COMMANDS`
- その場しのぎのシェルパイプラインよりも、リポジトリの自動化で既に使われているコマンドを優先する
- `SMOKE_COMMANDS` には、アプリの形態に応じて、最も軽量で信頼できる実行時の生存確認を選ぶ（例: ルート URL の読み込み、Electron の起動、CLI の `--help`、サービスのヘルスエンドポイント、既に存在する場合はモバイルシミュレーター／e2e ハーネス）
- 候補が複数ある場合は、実際にビルドされた成果物を動かしつつ、セットアップコストが最も小さいコマンドを優先する

### ステップ 3: 統合検証の実行

#### サブエージェントのディスパッチ（並列）

以下の検証観点は互いに独立しており、Agent ツールで**サブエージェント**としてディスパッチできる。エージェントは機能のスコープに基づいて最適な分割方法を決めるべきであり、適宜サブエージェントを分割、統合、またはスキップする。各サブエージェントは、GO/NO-GO の総合判断のためにメインコンテキストをきれいに保つよう、**構造化された所見の要約**を返す。

**典型的な検証観点**（適宜調整する）:
- **テストの実行**: テストスイート全体を実行し、パス／失敗を詳細とともに報告する
- **要件のカバレッジ**: 要件 → 実装のマトリクスを作り、ギャップを報告する
- **設計との整合**: アーキテクチャが design.md と一致することを確認し、ずれと依存関係の違反を報告する
- **タスク横断の統合**: データフロー、API の契約、共有状態の一貫性を確認する

単純な機能（タスクが少なく、スコープが小さい）の場合は、サブエージェントをディスパッチせず、メインコンテキストで確認を実行する。

#### 機械的チェック（コマンドを実行し、その結果を使う）

これらのチェックは機能レベルで適用する。コマンドの出力を主要なシグナルとして使う。

**A. テストスイート全体**
- 見つけた正規の全テストコマンドを実行する。終了コードを使う。
- テストが失敗した場合 → NO-GO。判断の余地はない。
- 正規のテストコマンドを特定できない場合 → `MANUAL_VERIFY_REQUIRED`

**B. 残存する TBD/TODO/FIXME**
- 実行: `grep -rn "TBD\|TODO\|FIXME\|HACK\|XXX" <files-in-feature-boundary>`
- この機能によって持ち込まれた一致が見つかった場合 → Warning（警告）として指摘する

**C. 残存するハードコードされたシークレット**
- 実行: `grep -rn "password\s*=\|api_key\s*=\|secret\s*=\|token\s*=" <files-in-feature-boundary>`（大文字小文字を区別しない）
- 環境変数の参照ではない一致が見つかった場合 → Critical（重大）として指摘する

**D. 実行時の生存確認（スモーク起動）**
- 見つけた正規のスモークコマンドを実行し、ビルドされた成果物が実際に起動して最初の使用可能な状態に到達することを示す。
- 該当する場合の例: ヘッドレスブラウザでルート URL を開き、起動時のコンソールエラーがゼロであることを求める。Electron を起動し、メインプロセスの ready シグナルと最初のレンダラーの読み込みを待つ。CLI を `--help` 付きで実行する。サービスを起動してそのヘルスエンドポイントにアクセスする。
- 起動時に実行時クラッシュ、未処理の例外、モジュール読み込みの失敗、ネイティブ ABI の不一致、または必須の環境変数／設定の欠如が発生した場合 → NO-GO。
- 信頼できるスモークコマンドを特定できない場合、または必要な実行環境が利用できない場合 → `MANUAL_VERIFY_REQUIRED`

#### 判断チェック（コードを読み、仕様と比較する）

**E. タスク横断の統合**
- タスク同士がインターフェース、データモデル、API の契約を共有している箇所を特定する
- タスク A の出力形式がタスク B の期待する入力と一致することを確認する
- タスク間で矛盾する前提（命名規約、エラーコード、データの形）がないか確認する
- 共有状態（データベーススキーマ、設定、環境）がタスク間で一貫していることを確認する
- 統合作業が、ある境界の振る舞いを別の境界に漏らすことによってではなく、意図された継ぎ目で行われていることを確認する

**F. 要件カバレッジのギャップ**
- すべての要件セクションを、少なくとも 1 つの完了済みタスクに対応付ける
- どの単一タスクも完全にはカバーしていない要件（横断的な要件）を特定する
- 複数のタスクによって部分的にカバーされているが、どのタスクによっても完全にはカバーされていない要件を特定する
- `requirements.md` の元のセクション番号を使う。`REQ-*` のような別名を作ってはならない

**G. 設計とのエンドツーエンドの整合**
- 全体のコンポーネントグラフが design.md と一致することを確認する
- 統合パターン（イベントフロー、API 境界、依存性注入）が設計どおりに機能することを確認する
- 依存方向が design.md のアーキテクチャに従っていること（上位方向への import がないこと）を確認する
- File Structure Plan（ファイル構成計画）が実際のファイル配置と一致することを確認する
- 元の設計からのアーキテクチャ上のずれを特定する
- `design.md` の元のセクション番号を使う

**G.5 境界の監査**
- 完了した作業を、設計の `Boundary Commitments`、`Out of Boundary`、`Allowed Dependencies`、`Revalidation Triggers`（境界の確約、境界外、許可された依存関係、再検証トリガー）と比較する
- ある領域が別の境界の責務をひそかに取り込んでしまった、タスク横断のはみ出しを特定する
- 「統合を楽にするため」に上流に埋め込まれた、下流固有の回避策を特定する
- 設計で宣言されていない、新たな隠れた依存関係や共有所有を特定する
- 再検証トリガーが発火した場合は、影響を受ける隣接の仕様や統合ポイントが実際に再確認されたことを確認する

**H. ブロックされたタスクと実装メモ**
- まだ `_Blocked:_` とマークされているタスクがないか確認する — その理由を報告し、機能の完成度への影響を評価する
- tasks.md の `## Implementation Notes` を見直し、注意が必要な横断的な知見がないか確認する

### ステップ 4: レポートの生成

`GO` を返す前に、機能レベルの主張に対して `kiro-verify-completion` のプロトコルを適用する。テストだけでは不十分である: テストスイート全体、実行時の生存確認、カバレッジ、統合、設計との整合、ブロックされたタスクの状態を証拠に含める。

是正を書く前に、具体的な失敗を所有者によって分類する:
- 欠陥が検証対象の機能に属する場合は `LOCAL`
- 根本原因が依存先、基盤、共有プラットフォーム、またはより前の仕様に属する場合は `UPSTREAM`
- 利用可能な証拠から所有者を確定できない場合は `UNCLEAR`

所有者が `UPSTREAM` の場合は、その問題をこの機能のローカルな是正にまとめてはならない。所有する上流の仕様を名指しし、その上流の修正が入った後にどの依存側の仕様を再検証すべきかを説明する。

spec.json で指定された言語でサマリーを出力する:

```
## Validation Report
- DECISION: GO | NO-GO | MANUAL_VERIFY_REQUIRED
- MECHANICAL_RESULTS:
  - Tests: PASS | FAIL (command and exit code)
  - TBD/TODO grep: CLEAN | <count> matches
  - Secrets grep: CLEAN | <count> matches
  - Smoke boot: PASS | FAIL | MANUAL_REQUIRED
- INTEGRATION:
  - Cross-task contracts: <status>
  - Shared state consistency: <status>
  - Boundary audit: <status>
- COVERAGE:
  - Requirements mapped: <X/Y sections covered>
  - Coverage gaps: <list of uncovered requirement sections>
- DESIGN:
  - Architecture drift: <findings>
  - Dependency direction: <violations if any>
  - File Structure Plan vs actual: <match/mismatch>
- OWNERSHIP: LOCAL | UPSTREAM | UNCLEAR
- UPSTREAM_SPEC: <feature-name | N/A>
- BLOCKED_TASKS: <list and impact assessment>
- REMEDIATION: <if NO-GO: specific, actionable steps to fix each issue>
```
（意味: DECISION=判定、MECHANICAL_RESULTS=機械的チェックの結果（Tests=テスト（コマンドと終了コード）、TBD/TODO grep・Secrets grep=CLEAN（該当なし）または一致件数、Smoke boot=スモーク起動）、INTEGRATION=統合（Cross-task contracts=タスク横断の契約、Shared state consistency=共有状態の一貫性、Boundary audit=境界の監査。`<status>`=状態）、COVERAGE=カバレッジ（Requirements mapped=対応付けた要件（Y セクション中 X セクションをカバー）、Coverage gaps=カバーされていない要件セクションの一覧）、DESIGN=設計（Architecture drift=アーキテクチャのずれ（所見）、Dependency direction=依存方向（違反があれば）、File Structure Plan vs actual=ファイル構成計画と実際の一致／不一致）、OWNERSHIP=所有者、UPSTREAM_SPEC=上流の仕様（機能名または N/A）、BLOCKED_TASKS=ブロックされたタスク（一覧と影響評価）、REMEDIATION=是正（NO-GO の場合: 各問題を修正するための具体的で実行可能な手順））

NO-GO の場合、REMEDIATION は必須である — 正確な問題と、何を変更する必要があるかを特定する。曖昧なフィードバックは受け入れられない。

## 重要な制約
- **厳格な最終ゲート**: `GO` を返すのは、すべての統合チェックに合格した場合のみである。具体的な失敗には `NO-GO` を返し、必須の検証を完了できなかった場合は `MANUAL_VERIFY_REQUIRED` を返す
- **利便性より境界の完全性**: 機能が責務を境界をまたいでにじませる（塗り広げる）ことでしか動作しない場合は、テストがパスしていても `GO` を返してはならない

## 安全策とフォールバック

### エラーシナリオ
- **実装が見つからない場合**: `[x]` のタスクが見つからなければ、"No implementations detected"（実装が検出されなかった）と報告する
- **テストコマンドが不明な場合**: `MANUAL_VERIFY_REQUIRED` を返し、どの検証コマンドが欠けているかを説明する。`GO` を返してはならない
- **仕様ファイルが欠けている場合**: spec.json/requirements.md/design.md が欠けていれば、エラーで停止する

### 次のステップのガイダンス

**GO 判定の場合**:
- 機能はエンドツーエンドで検証済みであり、デプロイまたは次の機能に進める状態である

**NO-GO 判定の場合**:
- REMEDIATION に列挙された問題に対処する
- 的を絞った修正のために `/kiro-impl {feature} [tasks]` を再実行する
- `/kiro-validate-impl {feature}` で再検証する

**MANUAL_VERIFY_REQUIRED の場合**:
- 機能を完了として扱ってはならない
- 欠けている正確な検証ステップ、または環境の前提条件を示す
