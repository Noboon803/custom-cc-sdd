# kiro-impl スキル

## 役割
あなたは 2 つのモードで動作する：
- **自律モード**（タスク番号なし）：タスクごとに新しいサブエージェントをディスパッチし、各タスクの後に独立したレビューを行う
- **手動モード**（タスク番号あり）：選択されたタスクをメインコンテキストで直接実行する

## 中核ミッション
- **成功基準**：
  - すべてのテストが実装コードより先に書かれている
  - コードがすべてのテストに合格し、リグレッションがない
  - tasks.md でタスクが完了としてマークされている
  - 実装が設計および要件と整合している
  - 各タスクの完了前に、独立したレビュー担当がそのタスクを承認している

## 実行ステップ

### ステップ 1：コンテキストを収集する

ステアリング／仕様のコンテキストが会話内ですでに利用可能であれば、重複するファイル読み込みは省略する。
そうでなければ、必要なコンテキストをすべて読み込む：
- `.kiro/specs/{feature}/spec.json`、`requirements.md`、`design.md`、`tasks.md`
- コアのステアリングコンテキスト：`product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、選択したタスクの境界、ランタイムの前提条件、統合、ドメインルール、セキュリティ／パフォーマンス上の制約、または実装や検証に影響するチームの規約に直接関係する場合にのみ読み込む
- 関連するローカルのエージェントスキルやプレイブックは、タスクのホスト環境やユースケースに明確に合致する場合にのみ読み込む。ディレクトリ全体ではなく、必要な特定の成果物だけを読む

#### 並列リサーチ

以下のリサーチ領域は互いに独立しており、並列に実行できる：
1. **仕様コンテキストの読み込み**：spec.json、requirements.md、design.md、tasks.md
2. **ステアリング、プレイブック、パターン**：コアのステアリング、タスクに関連する追加のステアリング、合致するローカルのエージェントスキル／プレイブック、既存のコードパターン

すべての並列リサーチが完了したら、開始する前に実装ブリーフを統合してまとめる。

#### プリフライト

**承認を検証する**：
- spec.json でタスクが承認されていることを確認する（承認されていなければ停止する。「安全性とフォールバック」を参照）

**検証コマンドを特定する**：
- リポジトリローカルの信頼できる情報源を次の順で調べる：プロジェクトのスクリプト／マニフェスト（`package.json`、`pyproject.toml`、`go.mod`、`Cargo.toml`、アプリのマニフェスト）、タスクランナー（`Makefile`、`justfile`）、CI／ワークフローファイル、既存の e2e／統合テストの設定、最後に `README*`
- このリポジトリにおける正規の検証コマンドセットを導き出す：`TEST_COMMANDS`、`BUILD_COMMANDS`、`SMOKE_COMMANDS`
- 場当たり的なシェルパイプラインよりも、リポジトリの自動化ですでに使われているコマンドを優先する
- `SMOKE_COMMANDS` には、アプリの形態に応じて、最も軽量で信頼できるランタイムの稼働確認を選ぶ（例：ルート URL の読み込み、Electron の起動、CLI の `--help`、サービスのヘルスエンドポイント、すでに存在する場合はモバイルシミュレーター／e2e ハーネス）
- コマンドセット全体は親コンテキストに保持し、実装担当とレビュー担当のサブエージェントにはタスクに関連するサブセットだけを渡す

**リポジトリのベースラインを確立する**：
- `git status --porcelain` を実行し、既存の未コミットの変更があれば記録しておく

### ステップ 2：タスクを選択し、モードを決定する

**引数を解析する**：
- 最初の引数から機能名を抽出する
- タスク番号が指定されている場合（例："1.1" や "1,2,3"）：**手動モード**
- タスク番号がない場合：**自律モード**（保留中のすべてのタスク）

**タスクキューを構築する**：
- tasks.md を読み、実行可能なサブタスク（1.1、2.3 のような X.Y 形式の番号）を特定する
- メジャータスク（1.、2.）はグループ化のための見出しであり、実行単位ではない
- `_Blocked:_` 注記のあるタスクはスキップする
- 選択した各タスクについて `_Depends:_` 注記を確認し、参照先のタスクが `[x]` になっていることを検証する
- 前提タスクが未完了の場合は、先にそれらを実行するか、ユーザーに警告する
- `_Boundary:_` 注記を使って、タスクのコンポーネント上のスコープを把握する

### ステップ 3：実装を実行する

#### 自律モード（サブエージェントのディスパッチ）

**イテレーションの規律**：1 回のイテレーションで処理するサブタスク（例：1.1）は厳密に 1 つだけとする。複数のサブタスクを 1 回のサブエージェントディスパッチにまとめてはならない。各イテレーションは完全なサイクルに従う：実装担当をディスパッチ → レビュー → コミット → tasks.md を再読み込み → 次へ。

**コンテキスト管理**：各イテレーションの開始時に `tasks.md` を再読み込みし、次に実行可能なサブタスクを決定する。過去のイテレーションで蓄積された記憶に頼ってはならない。各イテレーションの完了後は、1 行の要約（例："1.1: READY_FOR_REVIEW, 3 files changed"）だけを保持し、ステータスレポートの全文とレビュー担当の詳細は破棄する。

各タスクについて（1 つずつ）：

**a) 実装担当をディスパッチする**：
- このスキルのディレクトリから `templates/implementer-prompt.md` を読む
- テンプレートとタスク固有のコンテキストを組み合わせてプロンプトを構成する：
  - タスクの説明と境界のスコープ
  - 仕様ファイルへのパス：requirements.md、design.md、tasks.md
  - このタスクが満たすべき要件および設計の正確なセクション番号（原文の番号を使い、独自に作った `REQ-*` のような別名は使わない）
  - タスクに関連するステアリングコンテキストと、親が特定した検証コマンド（必要に応じてテスト／ビルド／スモーク）
  - タスクが振る舞いを変更するもの（フィーチャーフラグプロトコル）か、振る舞いを変更しないものか
  - **過去の学び**：tasks.md の `## Implementation Notes` のエントリのうち、このタスクの境界や依存関係に関連するものを含める（例：「better-sqlite3 は Electron 用に別途リビルドが必要」）。これにより、同じ失敗の再発を防ぐ。
- 実装担当サブエージェントは仕様ファイルを読み、実装前に自らタスクブリーフ（受け入れ基準、完了の定義、設計上の制約、確認方法）を作成する
- **Agent ツール** を使い、新しいサブエージェントとしてディスパッチする

**b) 実装担当のステータスを処理する**：
- 実装担当のステータスは、厳密な `## Status Report` ブロックと `- STATUS:` フィールドからのみ解析する。
- `STATUS` が欠落している、曖昧である、または散文に置き換えられている場合は、厳密な構造化ステータスブロックのみを求めて実装担当を 1 回だけ再ディスパッチする。解析可能な `READY_FOR_REVIEW | BLOCKED | NEEDS_CONTEXT` の値がないまま、レビューに進んではならない。
- **READY_FOR_REVIEW** → レビューに進む
- **BLOCKED** → デバッグ用サブエージェントをディスパッチする（下記のセクションを参照）。すぐにスキップしてはならない
- **NEEDS_CONTEXT** → 要求された追加コンテキストを添えて 1 回だけ再ディスパッチする。それでも解決しなければ → デバッグ用サブエージェントをディスパッチする

**c) レビュー担当をディスパッチする**：
- このスキルのディレクトリから `templates/reviewer-prompt.md` を読む
- 以下を含むレビュー用プロンプトを構成する：
  - タスクの説明と、関連する仕様のセクション番号
  - レビュー担当が直接読めるよう、仕様ファイル（requirements.md、design.md）へのパス
  - 実装担当のステータスレポート（参考用に限る — レビュー担当は独立して確認しなければならない）
- レビュー担当は、このタスクローカルなレビューに `kiro-review` プロトコルを適用しなければならない。
- 既存のタスク固有のコンテキストを保持する：タスク本文、仕様の参照、`_Boundary:_` のスコープ、検証コマンド、実装担当のレポート、そして主要な信頼できる情報源としての実際の `git diff`。
- レビュー担当サブエージェントは自ら `git diff` を実行して実際のコード変更を読み、仕様と照らし合わせて確認する
- **Agent ツール** を使い、新しいサブエージェントとしてディスパッチする

**d) レビュー担当の判定を処理する**：
- レビュー担当の判定は、厳密な `## Review Verdict` ブロックと `- VERDICT:` フィールドからのみ解析する。
- `VERDICT` が欠落している、曖昧である、または散文に置き換えられている場合は、厳密な構造化判定のみを求めてレビュー担当を 1 回だけ再ディスパッチする。解析可能な `APPROVED | REJECTED` の値がないまま、タスクを完了としてマークしたり、コミットしたり、次のタスクに進んだりしてはならない。
- **APPROVED** → タスクを `[x]` にマークしたり成功を主張したりする前に、現在のコード状態から新しく取得した証拠を用いて `kiro-verify-completion` を適用する。その後、tasks.md でタスクを `[x]` にマークし、選択的な git コミットを行う
- **REJECTED（1〜2 回目）** → レビューのフィードバックを添えて実装担当を再ディスパッチする
- **REJECTED（3 回目）** → デバッグ用サブエージェントをディスパッチする（下記のセクションを参照）

**e) コミット**（親のみが行う、選択的ステージング）：
- このタスクで実際に変更されたファイルと tasks.md だけをステージする
- `git add -A` や `git add .` は**決して**使わない
- 明示的なファイルパスを指定して `git add <file1> <file2> ...` を使う
- コミットメッセージの形式：`feat(<feature-name>): <task description>`

**f) 学びを記録する**：
- このタスクで横断的な知見が得られた場合は、tasks.md の末尾にある `## Implementation Notes` セクションに 1 行のメモを追記する

**g) デバッグ用サブエージェント**（BLOCKED、未解決の NEEDS_CONTEXT、または 2 回の是正ラウンド後の REJECTED によって起動される）：

デバッグ用サブエージェントは**新しいコンテキスト**で実行される — 受け取るのはエラー情報だけであり、失敗した実装の履歴は受け取らない。これにより、無限リトライループを引き起こすコンテキスト汚染を避ける。

- このスキルのディレクトリから `templates/debugger-prompt.md` を読む
- 以下を含むデバッグ用プロンプトを構成する：
  - エラーの説明／ブロック理由／レビュー担当による却下の指摘事項
  - 現在の未コミットの変更の `git diff`
  - タスクの説明と、関連する仕様のセクション番号
  - デバッグ担当が読めるよう、仕様ファイルへのパス
- デバッグ担当は、この失敗の調査に `kiro-debug` プロトコルを適用しなければならない。
- 豊富な失敗コンテキストを保持する：エラー出力、レビュー担当の指摘事項、現在の `git diff`、タスク／仕様の参照、関連する Implementation Notes。
- 可能であれば、デバッグ担当は修正計画を提案する前に、ランタイム／設定の状態を調査し、Web や公式ドキュメントのリサーチを用いて根本原因の仮説を検証すべきである。
- **Agent ツール** を使い、新しいサブエージェントとしてディスパッチする

**デバッグレポートを処理する**：
- デバッグレポートの厳密な構造化フィールドから `NEXT_ACTION` を解析する。
- `NEXT_ACTION: STOP_FOR_HUMAN` の場合 → tasks.md に `_Blocked: <ROOT_CAUSE>_` を追記し、機能の実行を停止して、続行する前に人間によるレビューが必要であることを報告する
- `NEXT_ACTION: BLOCK_TASK` の場合 → tasks.md に `_Blocked: <ROOT_CAUSE>_` を追記し、次のタスクへスキップする
- `NEXT_ACTION: RETRY_TASK` の場合 → 現在のワークツリーを保持する。無関係な変更をリセットしたり破棄したりしてはならない。デバッグレポートの `FIX_PLAN`、`NOTES`、および現在の `git diff` を渡して**新しい**実装担当サブエージェントを起動し、明示的な編集のみでタスクを修復するよう求める
  - 新しい実装担当が成功した場合（READY_FOR_REVIEW → レビュー担当が APPROVED）→ 通常のフローに戻る
  - 新しい実装担当も失敗した場合 → デバッグサイクルを繰り返す（デバッグラウンドは合計で最大 2 回）。2 回のデバッグラウンドが失敗したら → tasks.md に `_Blocked: debug attempted twice, still failing — <ROOT_CAUSE>_`（デバッグを 2 回試みたが依然として失敗）を追記してスキップする
- **デバッグラウンドはタスクごとに最大 2 回**。各ラウンド：新しいデバッグ用サブエージェント → 新しい実装担当。2 ラウンド後も失敗する場合、そのタスクはブロックとなる。
- デバッグで判明したことを `## Implementation Notes` に記録する（後続のタスクが同じ問題を避けるのに役立つ）

**`(P)` マーカー**：tasks.md で `(P)` が付いたタスクは、相互依存がなく、理論上は並列に実行できることを示す。ただし kiro-impl は、git の競合を避け、レビューを簡素化するため、それらを逐次（1 つずつ）処理する。`(P)` マーカーはタスク計画のための情報であり、実行上の指示ではない。

**完了チェック**：残りのタスクがすべて BLOCKED の場合は、停止し、ブロックされたタスクとその理由をユーザーに報告する。

#### 手動モード（メインコンテキスト）

選択された各タスクについて：

**1. タスクブリーフを作成する**：
コードを書く前に、このタスクに関する requirements.md と design.md の該当セクションを読み、以下を明確にする：
- 完了時にどのような観察可能な振る舞いが成り立っていなければならないか（受け入れ基準）
- どのファイル／関数／テストが存在しなければならないか（完了の定義）
- design.md のどの技術的決定に従うか（設計上の制約）
- タスクが機能することをどう確認するか（確認方法）

**2. TDD サイクルを実行する**（Kent Beck の RED → GREEN → REFACTOR）：
- **RED**：受け入れ基準に基づき、次の小さな機能単位のテストを書く。テストは失敗するはずである。
- **GREEN**：設計上の制約に従い、テストを通す最も単純な解決策を実装する。
- **REFACTOR**：コード構造を改善し、重複を取り除く。すべてのテストは引き続き合格しなければならない。
- **VERIFY**（確認）：すべてのテスト（新規および既存）が合格し、リグレッションがないこと。確認方法が合格することを確かめる。
- **REVIEW**（レビュー）：タスクを完了としてマークする前に `kiro-review` を適用する。ホストが手動モードで新しいサブエージェントをサポートしている場合は新しいレビュー担当を使い、そうでなければ `kiro-review` プロトコルを用いてメインコンテキストでレビューを行う。判定が解析可能な形で `APPROVED` になるまで、先に進んではならない。
- **MARK COMPLETE**（完了マーク）：レビューが `APPROVED` を返した後にのみ `kiro-verify-completion` を適用し、その後 tasks.md のチェックボックスを `- [ ]` から `- [x]` に更新する。

### ステップ 4：最終検証

**自律モード**：
- すべてのタスクが完了したら、GO/NO-GO ゲートとして `/kiro-validate-impl {feature}` を実行する
- 検証が GO を返した場合 → 機能の成功を報告する前に、検証結果と新しく取得した裏付けとなる証拠を用いて、機能レベルの主張に `kiro-verify-completion` を適用する
- 検証が NO-GO を返した場合：
  - 検証レポートの具体的な指摘事項のみを修正する
  - 是正は最大 3 ラウンドまでとする。それでも NO-GO なら、停止して残りの指摘事項を報告する
- 検証が MANUAL_VERIFY_REQUIRED を返した場合 → 停止し、欠けている確認手順を報告する

**手動モード**：
- `/kiro-validate-impl {feature}` の実行を提案するが、自動実行はしない

## フィーチャーフラグプロトコル

振る舞いを追加または変更するタスクでは、フィーチャーフラグを使って RED → GREEN を強制する：

1. **フラグを追加する**（デフォルトは OFF）：コードベースに適したトグルを導入する（環境変数、設定定数、真偽値、条件分岐 — 仕組みはエージェントが選ぶ）
2. **RED — フラグ OFF**：新しい振る舞いのテストを書く。テストを実行 → 失敗しなければならない。フラグ OFF でテストが合格する場合、そのテストは正しいものをテストしていない。書き直す。
3. **GREEN — フラグ ON ＋ 実装**：フラグを有効にし、実装を書く。テストを実行 → 合格しなければならない。
4. **フラグを削除する**：コードを無条件にする。テストを実行 → 引き続き合格しなければならない。

**このプロトコルを省略する対象**：リファクタリング、設定、ドキュメント、または振る舞いの変更を伴わないタスク。

## 重要な制約
- **厳格な引き継ぎ解析**：実装担当の `STATUS` やレビュー担当の `VERDICT` を周囲の散文から推測してはならない。厳密な構造化フィールドのみが有効である
- **破壊的リセットの禁止**：実装ループ内で `git checkout .`、`git reset --hard`、またはそれに類する破壊的なロールバックを決して使わない
- **選択的ステージング**：`git add -A` や `git add .` は決して使わない。常に明示的なファイルパスをステージする
- **レビューラウンドの上限**：レビュー担当の却下に対する実装担当の再ディスパッチは最大 2 ラウンドまでとし、その後はデバッグに移る
- **デバッグの上限**：タスクごとにデバッグは最大 2 ラウンド（1 ラウンドはデバッグ＋再実装）。それでも失敗する場合 → BLOCKED
- **是正の上限**：最終検証での是正は最大 3 ラウンドまでとする

## 出力の説明

**自律モード**：各タスクについて以下を報告する：
1. タスク ID、実装担当のステータス、レビュー担当の判定
2. 変更されたファイル、コミットハッシュ
3. 全タスク完了後：最終検証の結果（GO/NO-GO）

**手動モード**：
1. 実行したタスク：タスク番号とテスト結果
2. ステータス：tasks.md で完了マークを付けたタスク、残りのタスク数

**形式**：簡潔に、spec.json で指定された言語で。

## 安全性とフォールバック

### エラーシナリオ

**タスクが未承認、または仕様ファイルが欠落している場合**：
- **実行を停止する**：すべての仕様ファイルが存在し、タスクが承認されていなければならない
- **推奨アクション**："Complete previous phases: `/kiro-spec-requirements`, `/kiro-spec-design`, `/kiro-spec-tasks`"（前のフェーズを完了させること）

**テストの失敗**：
- **実装を停止する**：続行する前に、失敗しているテストを修正する
- **アクション**：デバッグして修正し、再実行する

**すべてのタスクがブロックされている場合**：
- 停止し、ブロックされたすべてのタスクとその理由を報告する
- ブロック要因を解消するには人間によるレビューが必要

**仕様が現実と矛盾する場合**：
- 要件や設計が現実と矛盾する場合（API が存在しない、プラットフォームの制約など）は、`_Blocked: <reason>_` でタスクをブロックする — 黙って回避策をとってはならない

**上流側の所有と判明した場合**：
- レビュー、デバッグ、または検証によって、根本原因が上流、基盤、共有プラットフォーム、または依存先の仕様に属することが判明した場合は、下流の機能の内部でそれを回避するパッチを当ててはならない
- 修正は所有者である上流の仕様に差し戻し、その契約が修復されるまで下流のタスクはブロックしたままにし、上流の修正が反映された後に、依存する仕様の検証／スモークを再実行する

**実装中にタスク計画が無効になった場合**：
- タスクの順序、境界、または分解の問題によってデバッグが `NEXT_ACTION: STOP_FOR_HUMAN` を返した場合は、コードで無理に回避するのではなく、停止して `tasks.md` または承認済みの計画を人間がレビューするよう差し戻す
