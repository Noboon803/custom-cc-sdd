# ステアリングの原則

ステアリングファイルは網羅的な仕様書ではなく、**プロジェクトメモリ**である。

---

## 内容の粒度

### Golden Rule（黄金律）
> 「新しいコードが既存のパターンに従っているなら、ステアリングを更新する必要はないはずだ。」

### ✅ 記述するもの
- 構成パターン（feature-first、レイヤード）
- 命名規則（PascalCase のルール）
- import 戦略（絶対パス vs 相対パス）
- アーキテクチャ上の意思決定（状態管理）
- 技術標準（主要なフレームワーク）

### ❌ 避けるもの
- 完全なファイル一覧
- すべてのコンポーネントの説明
- すべての依存関係
- 実装の詳細
- エージェント固有のツール用ディレクトリ（例: `.cursor/`、`.gemini/`、`.claude/`）
- `.kiro/` のメタデータディレクトリ（settings、automation）の詳細な記述

### 比較例

**悪い例**（仕様書的）:
```markdown
- /components/Button.tsx - Primary button with variants
- /components/Input.tsx - Text input with validation
- /components/Modal.tsx - Modal dialog
... (50+ files)
```

**良い例**（プロジェクトメモリ）:
```markdown
## UI Components (`/components/ui/`)
Reusable, design-system aligned primitives
- Named by function (Button, Input, Modal)
- Export component + TypeScript interface
- No business logic
```
（訳注: 悪い例は「バリエーション付きのプライマリボタン」「バリデーション付きのテキスト入力」「モーダルダイアログ」のようにファイルごとの説明を 50 ファイル以上列挙する形。良い例は「UI コンポーネント: 再利用可能で、デザインシステムに沿ったプリミティブ／機能で命名する（Button、Input、Modal）／コンポーネントと TypeScript インターフェースをエクスポートする／ビジネスロジックを含めない」とパターンだけを記述する形。）

## セキュリティ

決して含めてはならないもの:
- API キー、パスワード、認証情報
- データベース URL、内部 IP
- シークレットや機密データ

---

## 品質基準

- **単一ドメイン**: 1 ファイルにつき 1 トピック
- **具体的な例**: パターンをコードで示す
- **根拠を説明する**: なぜその決定がなされたのか
- **保守しやすいサイズ**: 通常 100〜200 行

---

## 保全（更新時）

- ユーザーのセクションとカスタムの例を保全する
- デフォルトは追記方式（置き換えるのではなく追加する）
- `updated_at` タイムスタンプを追加する
- 変更の理由を記載する

---

## 注記

- テンプレートは出発点であり、必要に応じてカスタマイズする
- コアのステアリングと同じ粒度の原則に従う
- すべてのステアリングファイルはプロジェクトメモリとして読み込まれる
- `.kiro/specs/` と `.kiro/steering/` への軽い参照は許容される。それ以外の `.kiro/` ディレクトリは避ける
- カスタムファイルはコアファイルと同等に重要である

---

## ファイルごとの重点

- **product.md**: 目的、価値、ビジネス上のコンテキスト（網羅的な機能一覧ではない）
- **tech.md**: 主要なフレームワーク、標準、規約（すべての依存関係ではない）
- **structure.md**: 構成パターン、命名ルール（ディレクトリツリーではない）
- **カスタムファイル**: 専門的なパターン（API、テスト、セキュリティなど）
