# ギャップ分析プロセス

## 目的
実装戦略の意思決定の判断材料とするために、要件と既存コードベースの間のギャップを分析する。

## 分析フレームワーク

### 1. 現状調査

- ドメインに関連する資産を洗い出す:
  - 主要なファイル／モジュールとディレクトリ構成
  - 再利用可能なコンポーネント／サービス／ユーティリティ
  - 支配的なアーキテクチャパターンと制約

- 規約を抽出する:
  - 命名、レイヤリング、依存の方向
  - import/export のパターンと依存関係のホットスポット
  - テストの配置と方針

- 統合面を記録する:
  - データモデル／スキーマ、API クライアント、認証メカニズム

### 2. 要件の実現可能性分析

- EARS 形式の要件から、技術的なニーズを列挙する:
  - データモデル、API／サービス、UI／コンポーネント
  - ビジネスルール／検証
  - 非機能要件: セキュリティ、パフォーマンス、スケーラビリティ、信頼性

- ギャップと制約を特定する:
  - 現在のコードベースに不足している機能
  - 後で調査すべき未知の事項（"Research Needed"（要調査）としてマークする）
  - 既存のアーキテクチャとパターンに由来する制約

- 複雑さのシグナルを記録する:
  - 単純な CRUD／アルゴリズム的ロジック／ワークフロー／外部統合

### 3. 実装アプローチの選択肢

#### 選択肢 A: 既存コンポーネントを拡張する
**検討すべき場合**: 機能が既存の構造に自然に収まる場合

- **拡張するファイル／モジュール**:
  - 変更が必要な具体的なファイルを特定する
  - 既存機能への影響を評価する
  - 後方互換性の懸念を評価する

- **互換性の評価**:
  - 拡張が既存のインターフェースを尊重しているか確認する
  - 利用側に破壊的変更がないことを確認する
  - テストカバレッジへの影響を評価する

- **複雑さと保守性**:
  - 機能追加による認知負荷を評価する
  - 単一責任の原則が維持されているか確認する
  - ファイルサイズが管理可能な範囲に収まるか評価する

**トレードオフ**:
- ✅ 新規ファイルが最小限で、初期開発が速い
- ✅ 既存のパターンとインフラを活用できる
- ❌ 既存コンポーネントが肥大化するリスクがある
- ❌ 既存のロジックを複雑にする可能性がある

#### 選択肢 B: 新しいコンポーネントを作成する
**検討すべき場合**: 機能が独立した責務を持つ、または既存コンポーネントがすでに複雑である場合

- **新規作成の根拠**:
  - 関心の明確な分離が新しいファイルを正当化する
  - 既存コンポーネントがすでに複雑である
  - 機能が独自のライフサイクルや依存関係を持つ

- **統合ポイント**:
  - 新しいコンポーネントが既存システムにどう接続するか
  - 公開する API やインターフェース
  - 既存コンポーネントへの依存

- **責務の境界**:
  - 新しいコンポーネントが何を担うかの明確な定義
  - 既存コンポーネントとのインターフェース
  - データフローと制御フロー

**トレードオフ**:
- ✅ 関心がきれいに分離される
- ✅ 単独でテストしやすい
- ✅ 既存コンポーネントの複雑さを軽減する
- ❌ 行き来するファイルが増える
- ❌ 慎重なインターフェース設計が必要になる

#### 選択肢 C: ハイブリッドアプローチ
**検討すべき場合**: 拡張と新規作成の両方を必要とする複雑な機能の場合

- **組み合わせ戦略**:
  - どの部分で既存コンポーネントを拡張するか
  - どの部分で新しいコンポーネントが妥当か
  - それらがどう相互作用するか

- **段階的な実装**:
  - 初期フェーズ: 必要最小限の変更
  - 後続フェーズ: リファクタリングまたは新しいコンポーネント
  - 必要に応じた移行戦略

- **リスク軽減**:
  - 段階的なロールアウトの方法
  - フィーチャーフラグまたは設定
  - ロールバック戦略

**トレードオフ**:
- ✅ 複雑な機能に対してバランスの取れたアプローチ
- ✅ 反復的な改善が可能
- ❌ より複雑な計画が必要
- ❌ うまく調整しないと一貫性を欠く可能性がある
### 4. ギャップ分析のスコープ外

- 深い調査活動は設計フェーズに回す。
- 未知の事項は、簡潔な "Research Needed"（要調査）項目としてのみ記録する。

### 5. 実装の複雑さとリスク

  - 工数（Effort）:
    - S（1〜3 日）: 既存パターン、依存は最小限、統合は単純
    - M（3〜7 日）: いくつかの新しいパターン／統合、中程度の複雑さ
    - L（1〜2 週間）: 大きな機能、複数の統合やワークフロー
    - XL（2 週間以上）: アーキテクチャの変更、不慣れな技術、広範な影響
  - リスク（Risk）:
    - High: 未知の技術、複雑な統合、アーキテクチャの転換、パフォーマンス／セキュリティの道筋が不明確
    - Medium: 指針のある新しいパターン、管理可能な統合、既知のパフォーマンス解決策
    - Low: 確立されたパターンの拡張、慣れた技術、明確なスコープ、統合は最小限

### 出力チェックリスト

- ギャップにタグ（Missing / Unknown / Constraint: 不足／不明／制約）を付けた、要件とアセットの対応表（Requirement-to-Asset Map）
- 選択肢 A/B/C と、それぞれの短い根拠およびトレードオフ
- 工数（S/M/L/XL）とリスク（High/Medium/Low）、それぞれ 1 行の根拠付き
- 設計フェーズへの推奨事項:
  - 推奨するアプローチと主要な意思決定
  - 引き継ぐ調査項目

## 原則

- **意思決定より情報**: 最終的な選択ではなく、分析と選択肢を提供する
- **実行可能な複数の選択肢**: 該当する場合は信頼に足る代替案を提示する
- **ギャップと前提の明示**: 未知の事項と制約を明確に示す
- **コンテキストを踏まえる**: 既存のパターンとアーキテクチャ上の制限に合わせる
- **工数とリスクの透明性**: ラベルの根拠を簡潔に示す
