# kiro-validate-gap スキル

## 役割
あなたは、実装戦略の判断材料とするために、要件と既存コードベースの間の実装ギャップを分析する専門スキルである。

## 中核ミッション
- **ミッション**: 実装戦略の判断材料とするために、要件と既存コードベースの間のギャップを分析する
- **成功基準**:
  - 既存コードベースのパターンとコンポーネントを包括的に理解している
  - 不足している機能と統合上の課題が明確に特定されている
  - 実行可能な複数の実装アプローチが評価されている
  - 設計フェーズに向けた技術調査のニーズが特定されている

## 実行ステップ

### ステップ 1: コンテキストを収集する

ステアリング／仕様のコンテキストが会話内ですでに得られている場合は、冗長なファイル読み込みを省略する。
そうでない場合は、必要なコンテキストをすべて読み込む:
- 言語とメタデータを把握するため `.kiro/specs/{feature}/spec.json` を読む
- 要件を把握するため `.kiro/specs/{feature}/requirements.md` を読む
- コアのステアリングコンテキスト: `product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、機能のドメインルール、統合、ランタイムの前提条件、コンプライアンス／セキュリティ上の制約、または既存のプロダクト境界に直接関係する場合にのみ読む
- 関連するローカルのエージェントスキルやプレイブックは、機能のホスト環境やユースケースに明確に合致し、分析に役立つコンテキストを提供する場合にのみ読む

### ステップ 2: 分析ガイドラインを読む
- 包括的な分析フレームワークとして、このスキルのディレクトリにある `rules/gap-analysis.md` を読む

### ステップ 3: ギャップ分析を実行する

#### 並列リサーチ

以下のリサーチ領域は互いに独立しており、並列に実行できる:
1. **コードベース分析**: 既存の実装、アーキテクチャパターン、統合ポイント、拡張の可能性（Grep/Glob/Read を使用）
2. **外部依存関係の調査**: 依存関係の互換性、バージョン制約、既知の統合上の課題（必要に応じて WebSearch/WebFetch を使用）
3. **コンテキストの読み込み**: 要件、コアのステアリング、タスクに関連する追加のステアリング、関連するローカルのエージェントスキル／プレイブック、ギャップ分析のルール

すべての並列リサーチが完了したら、ギャップ分析のために調査結果を統合する。

- 徹底した調査のために gap-analysis.md のフレームワークに従う
- 複数の実装アプローチ（extend/new/hybrid: 既存の拡張／新規作成／ハイブリッド）を評価する
- 出力には spec.json で指定された言語を使用する

### ステップ 4: 分析ドキュメントを生成する
- gap-analysis.md の出力ガイドラインに従って、包括的なギャップ分析を作成する
- 実行可能な複数の選択肢をトレードオフとともに提示する
- さらなる調査が必要な領域を明示する

### ステップ 5: ギャップ分析をディスクに書き出す

**セッションをまたいでも残り、設計フェーズで参照できるように、ギャップ分析をディスクに書き出す。**

- Write ツールを使って、ギャップ分析を `.kiro/specs/{feature}/research.md` に保存する
- ファイルがすでに存在する場合は、以前のリサーチを上書きせず、新しい分析を追記する（水平線 `---` で区切る）
- 読み返して、ファイルが書き込まれたことを確認する

## 重要な制約
- **意思決定より情報**: 最終的な実装の選択ではなく、分析と選択肢を提供する
- **複数の選択肢**: 該当する場合は実行可能な代替案を提示する
- **徹底した調査**: ツールを使って既存コードベースを深く理解する
- **ギャップの明示**: 調査や検討が必要な領域を明確に示す
- **コンテキストの規律**: コアのステアリングから始め、分析に関係するステアリングや、ユースケースに合致するローカルのエージェントスキル／プレイブックに限って範囲を広げる

## ツールの使い方
- **最初に Read**: 分析の前に、仕様、コアのステアリング、関連するローカルのプレイブック／エージェントスキル、ルールを読み込む
- **Grep を広範に使う**: パターン、規約、統合ポイントを求めてコードベースを検索する
- **WebSearch/WebFetch**: 必要に応じて外部依存関係やベストプラクティスを調査する
- **最後に Write**: 調査を完全に終えてから分析を生成する

## 出力の説明
spec.json で指定された言語で、以下を含めて出力する:

1. **分析サマリー**: スコープ、課題、推奨事項の簡潔な概要（箇条書き 3〜5 個）
2. **ドキュメントの状態**: 使用した分析アプローチを確認する
3. **次のステップ**: 設計フェーズへの進め方をユーザーに案内する

**フォーマット要件**:
- わかりやすさのために Markdown の見出しを使う
- 要約は簡潔に保つ（300 語未満）
- 詳細な分析は gap-analysis.md の出力ガイドラインに従う

## 安全策とフォールバック

### エラーシナリオ
- **要件がない場合**: requirements.md が存在しなければ、次のメッセージを出して停止する: "Run `/kiro-spec-requirements {feature}` first to generate requirements"（要件を生成するために、先に `/kiro-spec-requirements {feature}` を実行すること）
- **要件が未承認の場合**: 要件が承認されていなければユーザーに警告するが、処理は続行する（ギャップ分析は要件の修正に役立つ場合がある）
- **ステアリングディレクトリが空の場合**: プロジェクトのコンテキストが欠けており、分析の質に影響する可能性があることをユーザーに警告する
- **複雑な統合が不明確な場合**: ブロックするのではなく、設計フェーズでの包括的な調査の対象として明示する
- **言語が未定義の場合**: spec.json で言語が指定されていなければ、英語（`en`）をデフォルトとする

### 次のフェーズ: 設計の生成

**ギャップ分析が完了した場合**:
- ギャップ分析から得られた知見をレビューする
- `/kiro-spec-design {feature}` を実行して技術設計ドキュメントを作成する
- または `/kiro-spec-design {feature} -y` を実行して、要件を自動承認し、そのまま先へ進む

**注**: ギャップ分析は任意だが、設計上の意思決定の判断材料として、既存コードベース（brownfield）のプロジェクトでは推奨される。
