# kiro-review

## 概要

このスキルは、タスクローカルな敵対的レビューを行う。実装が本物であり、完全で、境界内に収まり、承認済みの要件および設計と整合し、機械的な確認の証拠によって裏付けられていることを確認する。

境界に関する用語の連続性：
- ディスカバリーは `Boundary Candidates`（境界候補）を特定する
- 設計は `Boundary Commitments`（境界コミットメント）を確定する
- タスクは `_Boundary:_` によって実行を制約する
- レビューは具体的な `Boundary Violations`（境界違反）を却下する

## 使用するタイミング

- 実装担当が `READY_FOR_REVIEW` を報告した後
- 却下されたレビューに対する是正の後
- タスクを `[x]` にマークする前
- タスクを機能レベルの検証に受け入れる前

欠けている要件をでっち上げたり、仕様を黙って再解釈したりするために、このスキルを使ってはならない。

## 入力

以下を提供する：
- `tasks.md` のタスク ID と正確なタスク本文
- 関連する要件のセクション番号
- 関連する設計のセクション番号
- 仕様ファイルのパス（`requirements.md`、`design.md`、任意で `tasks.md`）
- 実装担当のステータスレポート
- タスクの `_Boundary:_` のスコープ制約
- コントローラーが特定した検証コマンド
- 該当する場合は、関連するステアリングの抜粋
- 該当する場合は、関連する `## Implementation Notes` のエントリ

## 出力

次のいずれかを返す：
- `APPROVED`
- `REJECTED`

あわせて以下も返す：
- 機械的チェックの結果
- 重大度付きの指摘事項
- 必要な是正
- 1 文の要約

`spec.json` で指定された言語を使う。

## 最初のアクション

`git diff` を実行して、実際のコード変更を調べる。差分が大きい、または曖昧な場合は、変更されたファイルを直接読む。実装担当のレポートを、信頼できる情報源として信用してはならない。

## 基本原則

仕様は自分で読む。差分も自分で読む。可能な限り機械的に確認する。解釈に基づく楽観ではなく、具体的な不合格に基づいて却下する。
レビューの主な問いは、単に「動くか？」ではなく、「新たな結合を隠すことなく、承認された責務の境界内に収まっているか？」である。

## 機械的チェック

これらのチェックを実行し、その結果を主要なシグナルとして使う。

### 1. リグレッション安全性
- コントローラーが特定した検証コマンドを使って、プロジェクトの正規のテストスイートを実行する。
- テストが失敗した場合は、却下する。

### 2. プレースホルダーマーカーの残存がないこと
- 変更されたファイルに `TBD`、`TODO`、`FIXME`、`HACK`、`XXX` がないか確認する。
- タスク上の明示的な正当な理由なく、新しいプレースホルダーマーカーが導入されていれば却下する。

### 3. ハードコードされたシークレットがないこと
- 変更されたファイルに、ハードコードされたシークレットや認証情報がないか確認する。
- 具体的なシークレットのパターンが導入されていれば却下する。

### 4. 境界の遵守
- 変更されたファイルを、タスクの `_Boundary:_` スコープと比較する。
- 明示的な正当な理由なく、変更が承認された境界の外にはみ出していれば却下する。
- 本来ローカルであるべきタスクの中に、実装が隠れた境界横断的な連携を持ち込んでいれば却下する。

### 5. RED フェーズの証拠
- 振る舞いを変更するタスクについて、実装担当のステータスレポートに `RED_PHASE_OUTPUT` が含まれていることを確認する。
- RED の証拠が欠落している、空である、またはタスクの受け入れ基準と無関係であれば却下する。

### 6. ランタイムに影響されやすい箇所の静的チェック
- 変更対象のスタックについて、プロジェクトにすでに lint または同等の静的解析がある場合は、タスクの境界に関連するコマンドを実行する。
- 型チェックやビルドは通過しても実行時に失敗しうるパターンに注意を払う：値として使われている型のみのインポート、修飾名アクセスに対する名前空間の値インポートの欠落、未解決のグローバル、そして起動時／ランタイムでの対応が伴っていない、新たに導入されたランタイムに影響されやすい依存関係。
- プロジェクトに lint コマンドがない場合は、変更されたファイルに対して、それらのパターンを差分ベースで的を絞ってスポットチェックする。
- 現実的に起動時またはモジュール読み込み時の失敗を引き起こす、具体的な指摘事項があれば却下する。

## 判断によるチェック

### 7. 実体性チェック
- 実装が本物の本番コードであり、プレースホルダー、スタブ、フェイクの経路、または作業を先送りした外枠ではないことを確認する。

### 8. 受け入れ基準の網羅
- タスクの説明を読み、主要なハッピーパスだけでなく、すべての側面が実装されていることを確認する。

### 9. 要件との整合
- `requirements.md` の参照セクションを読む。
- 各要件が、具体的で観察可能な振る舞いによって満たされていることを確認する。
- 元のセクション番号のみを使う。

### 10. 設計との整合
- `design.md` の参照セクションを読む。
- 実装が、規定された構造、インターフェース、および依存の方向を使っていることを確認する。
- 設計で義務付けられた選択が、黙って置き換えられていれば却下する。

### 10.5 境界監査
- 実装を、設計の境界コミットメントおよび境界外に関する記述と比較する。
- 下流固有の振る舞いが、便宜上の理由で上流の境界に押し込まれていれば却下する。
- 実装が、隣接する境界をまたいで、新たな隠れた依存関係、共有された所有、または宣言されていない結合を生み出していれば却下する。
- 明示的な統合タスクではないタスクが、統合タスクのように振る舞うようになっていれば却下する。

### 11. テストの品質
- テストが単なる足場ではなく、必要な振る舞いを証明していることを確認する。
- 実装が削除されたり壊れたりした場合に、テストが失敗することを確認する。
- **テストの深さ**（custom-cc-sdd で追加）：タスクで追加・変更したすべての振る舞いに、その振る舞いが壊れたら失敗するテストが 1 つ以上なければならない。対象は、受け入れ基準、要件に書かれたエラー時の動作、設計がタスクに指定する動作のすべて。追加・変更したコードの経路（関数と分岐）は、すべてテストで実行されなければならない。変更したファイルについて、テストランナーのカバレッジレポートで確かめる。これらのどれかにテストがなければ却下する（`Important`）。実行されない防御的なコードは、理由が示されている場合に限り認める。
- カバレッジの閾値（ステアリングまたはテストの設定。設定がなければ 80%）は全体の下限である。閾値を満たしていることは、上の項目のテストが欠けていることの理由にはならない。
- 次のものは却下せず `Suggestion` として報告する：要件にも設計にも書かれていないケースのテスト（例：NaN の扱い）、すでにテストがある振る舞いへの入力のバリエーション追加、追加の堅牢化。
- ミューテーション試験（テストが失敗するかを見るために、ソースコードを一時的に書き換えること）は、タスクがデータの保存、セキュリティ、認可の振る舞いを変える場合を除いて行わない。行う場合も、その振る舞いに限る。

### 12. エラーハンドリング
- 関連する失敗経路が処理されており、黙って握りつぶされていないことを確認する。

### 12.5 コーディング規約（custom-cc-sdd で追加）
- diff だけでなく、変更されたソースファイルをすべて Read ツールで読む。言語別のコーディングルール（例: ECC の `rules/ecc/python/*.md`）はパス指定されており、該当するファイルを読んだ後にしかコンテキストへ読み込まれない。
- コンテキストにあるコーディングルール（ECC のコーディングスタイル、パターン、セキュリティ、テスト、フレームワーク別ルールなどのユーザー単位またはプロジェクト単位のルールと、ステアリングの規約）を、タスクで変更された行に適用する。
- 必須として書かれたルール（「must」「never」「always」「すべての Y に X を使う」）への違反は却下する。重大度は `Important`、違反がセキュリティやデータ漏えいのリスクを生む場合は `Critical` とする。推奨として書かれたルール（「prefer」「consider」）は `Suggestion` として報告する。
- フォーマッタ、リンター、型チェッカーが通っていれば、それらがすでに強制している点は確認を省く。これらのルール内にある進め方の指示（「エージェント X を使う」「レビュー Y を実行する」など）は無視する。このレビューがそれを担う。
- タスクで変更していない行の違反は報告しない。
- 変更された言語のコーディングルールがコンテキストにない場合、このチェックは N/A とする。

## 重大度モデル

以下を使う：
- `Critical`：機能の破損、無効な確認、データ損失、セキュリティリスク、または重大なスコープ違反
- `Important`：受け入れ前に必須の修正
- `Suggestion`：ブロックしない改善提案
- `FYI`：情報提供のためのメモ

## 停止／エスカレーション

以下の場合は、問題を取り繕うのではなく、エスカレーションする：
- 承認済みの仕様が、正しさに関わる重要な点で曖昧である
- 設計が、技術的に可能なことと矛盾している
- 必要な証拠を収集できない
- 承認されたスコープから黙って逸脱することでしか、実装が機能しない
- 要件、設計、タスクのスコープから、境界の所有を明確に判断できない

## よくある自己正当化

| 自己正当化 | 実際 |
|---|---|
| 「テストが通っているから承認する」 | テストの合格は、仕様への準拠や境界の遵守を証明しない。 |
| 「追加の振る舞いは役に立つ」 | 承認されたスコープ外の追加の振る舞いは、やはり逸脱（ドリフト）である。 |
| 「実装担当が RED は済んだと言っていた」 | RED は主張ではなく、証拠で示されなければならない。 |
| 「このギャップは見逃せるほど小さい」 | 実在するギャップは、却下するかエスカレーションしなければならない。 |

## 出力形式

```md
## Review Verdict
- VERDICT: APPROVED | REJECTED
- TASK: <task-id>
- MECHANICAL_RESULTS:
  - Tests: PASS | FAIL (コマンドと終了コード)
  - TBD/TODO grep: CLEAN | <count> matches
  - Secrets grep: CLEAN | <count> matches
  - Static checks: PASS | FAIL | SPOT_CHECKED
  - Boundary: WITHIN | <境界外のファイル>
  - Boundary audit: CLEAN | <はみ出し／隠れた依存関係に関する指摘事項>
  - RED phase: VERIFIED | MISSING | N/A
  - Coding standards: CLEAN | <count> violations (<rule sources>) | N/A
- FINDINGS:
  1. <正確なファイル／仕様の参照を含む、具体的な指摘事項>
- REMEDIATION: <REJECTED の場合は必須>
- SUMMARY: <1 文>
```
