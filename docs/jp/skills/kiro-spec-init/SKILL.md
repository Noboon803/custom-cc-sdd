# 仕様の初期化

<instructions>
## 中核タスク
プロジェクト説明（$ARGUMENTS）から一意の機能名を生成し、仕様の構造を初期化する。

## 実行手順
1. **ブリーフの確認**: `.kiro/specs/{feature-name}/brief.md` が存在する場合（`/kiro-discovery` によって作成されたもの）、それを読む。ブリーフには、ディスカバリーセッションで得られた課題、アプローチ、スコープ、制約が含まれている。これを使ってプロジェクト説明を事前に埋め、ブリーフがすでに答えている確認質問は省略する。
2. **意図の明確化**: requirements.md の Project Description（プロジェクト説明）には、次の 3 つの要素が含まれていなければならない: (a) 誰が課題を抱えているか、(b) 現在の状況、(c) 何が変わるべきか。brief.md が存在し、これらを網羅している場合は手順 3 に進む。そうでない場合は、先に進む前にユーザーに明確化を求める。必要なだけ質問すること。自分の推測でギャップを埋めてはならない。
3. **一意性の確認**: `.kiro/specs/` に名前の衝突がないか確認する。ディレクトリがすでに存在し、中身が `brief.md` のみ（`spec.json` がない）の場合は、そのディレクトリを使用する（ディスカバリーが作成したもの）。
4. **ディレクトリの作成**: `.kiro/specs/[feature-name]/`（ディスカバリーによってすでに存在する場合は省略する）
5. **テンプレートを使ったファイルの初期化**:
   - `.kiro/settings/templates/specs/init.json` を読む
   - `.kiro/settings/templates/specs/requirements-init.md` を読む
   - プレースホルダーを置換する:
     - `{{FEATURE_NAME}}` → 生成した機能名
     - `{{TIMESTAMP}}` → 現在の ISO 8601 タイムスタンプ
     - `{{PROJECT_DESCRIPTION}}` → brief.md があればそこから、なければ $ARGUMENTS
     - `ja` → 言語コード（ユーザーの入力言語から検出する。デフォルトは `en`）（訳注: 原文でもこの行は `ja` と記載されている。インストール時に言語コードのプレースホルダーが `ja` に置換された結果と思われる）
   - `spec.json` と `requirements.md` を仕様ディレクトリに書き込む

## 重要な制約
- 要件、設計、タスクを生成してはならない。このスキルは spec.json と requirements.md の作成のみを行う。
</instructions>

## 出力の説明
`spec.json` で指定された言語で、次の構成に従って出力する:

1. **生成した機能名**: `feature-name` 形式で、1〜2 文の根拠を添える
2. **プロジェクトの要約**: 簡潔な要約（1 文）
3. **作成したファイル**: フルパスの箇条書き
4. **次のステップ**: `/kiro-spec-requirements <feature-name>` を示すコマンドブロック

**書式要件**:
- Markdown の見出し（##, ###）を使う
- コマンドはコードブロックで囲む
- 出力全体を簡潔に保つ（250 語未満）
- `spec.json.language` に従い、明確でプロフェッショナルな言葉遣いにする

## 安全策とフォールバック
- **機能名が曖昧な場合**: 機能名の生成がはっきりしない場合は、2〜3 個の候補を提案し、ユーザーに選択してもらう
- **テンプレートの欠落**: `.kiro/settings/templates/specs/` にテンプレートファイルが存在しない場合は、欠落している具体的なファイルパスを添えてエラーを報告し、リポジトリのセットアップを確認するよう提案する
- **ディレクトリの衝突**: 機能名がすでに存在する場合は、数字の接尾辞を付加し（例: `feature-name-2`）、衝突を自動的に解決したことをユーザーに通知する
- **書き込みの失敗**: 具体的なパスを添えてエラーを報告し、権限またはディスク容量を確認するよう提案する
