# kiro-debug

## 概要

このスキルは、新しいコンテキストでの根本原因調査のためのものである。ローカルの証拠、ランタイム／設定の調査、そして利用可能な場合は外部のドキュメントや issue のリサーチを組み合わせる。推測先行のデバッグのためのパッチ生成器ではない。

## 使用するタイミング

- 実装担当が `BLOCKED` を報告した
- 是正の後も、レビュー担当による却下が繰り返される
- 検証が予期せず失敗する
- タスクが、ランタイムやプラットフォームの現実と矛盾しているように見える
- 同じ失敗が、複数回の修正の試みを経ても残っている

証拠を集める前に、修正について推測するためにこのスキルを使ってはならない。

## 入力

以下を提供する：
- 正確な失敗の症状、またはブロック要因の記述
- エラーメッセージ、スタックトレース、および失敗したコマンドの出力
- 現在の `git diff`、または未コミットの失敗した変更の要約
- タスクブリーフ：何を構築しようとしていたか
- 失敗がレビューでの却下によるものであれば、レビュー担当のフィードバック
- 関連する仕様ファイルのパス（`requirements.md`、`design.md`）
- 関連する要件／設計のセクション番号
- 関連する `## Implementation Notes`
- すでに判明しているランタイムまたは環境の制約

## 出力

以下を返す：
- `ROOT_CAUSE`
- `CATEGORY`
- `FIX_PLAN`
- `VERIFICATION`
- `NEXT_ACTION: RETRY_TASK | BLOCK_TASK | STOP_FOR_HUMAN`
- `CONFIDENCE: HIGH | MEDIUM | LOW`
- `NOTES`

`spec.json` で指定された言語を使う。

## 手法

### 1. エラーを注意深く読む
以下を抽出する：
- 正確なエラーテキスト
- スタックトレースまたは失敗箇所
- 失敗を引き起こしたコマンド
- 失敗が決定的（毎回再現する）か、断続的か

### 2. ローカルのランタイムとリポジトリの状態を調査する
リポジトリ内のローカルな証拠を調べる：
- `package.json`、`pyproject.toml`、`go.mod`、`Makefile`、`README*`
- ビルド設定
- `tsconfig` または同等の言語／ランタイムの設定
- ランタイム固有の設定
- 依存関係のバージョンとスクリプト
- `git diff` に含まれる、関連する変更ファイル

### 3. 可能であれば Web を検索する
Web アクセスが利用可能であれば、以下を検索する：
- 正確なエラーメッセージ
- 技術と症状の組み合わせ
- 公式ドキュメント
- バージョン固有の issue トラッカーや移行ガイド

以下を優先する：
- 公式ドキュメント
- 公式のリポジトリ／issue
- バージョン固有の参考情報
- ランタイム固有のドキュメント

### 4. 根本原因を分類する
次のカテゴリから 1 つを使う：
- `MISSING_DEPENDENCY`
- `RUNTIME_MISMATCH`
- `MODULE_FORMAT`
- `NATIVE_ABI`
- `CONFIG_GAP`
- `LOGIC_ERROR`
- `TASK_ORDERING_PROBLEM`
- `TASK_DECOMPOSITION_PROBLEM`
- `SPEC_CONFLICT`
- `EXTERNAL_DEPENDENCY`

### 5. 最小かつ安全な次のアクションを決める
問題が、このリポジトリ内で以下によって修正できるかを判断する：
- ファイルの編集
- 設定の調整
- 依存関係の追加または修正
- コードの再構成

問題が、現在の承認済みタスク計画の範囲内で、リポジトリ内で修正可能な場合は、`NEXT_ACTION: RETRY_TASK` を使う。

### 6. タスク計画がまだ有効かを判断する
現在の承認済みタスク計画を、書かれたとおりに実行してもまだ安全かどうかを判断する。

以下の場合は `NEXT_ACTION: STOP_FOR_HUMAN` を優先する：
- このタスクより前に存在すべき前提タスクが欠けている
- 現在のタスクが、未完了の作業に対して誤った順序に置かれている
- 現在のタスクの境界が誤っており、分割または統合すべきである
- タスクが大きすぎる、または曖昧すぎて、現在の実装ループ内で安全に修正できない

`NEXT_ACTION: BLOCK_TASK` は、現在のタスクは停止すべきだが、キューの残りは引き続き安全に進められる場合にのみ使う。

`tasks.md` や承認済みの計画を見直す代わりに、力任せのコード修正を提案してはならない。

## 重要なルール

複数の修正を乱射するような計画を提案してはならない。まず根本原因を特定し、それから最小限の妥当な修正計画を作成する。真の問題が仕様の矛盾やアーキテクチャの問題であれば、そうはっきり述べる。

## 停止／エスカレーション

ブロック要因が本当に以下を必要とする場合は、`NEXT_ACTION: STOP_FOR_HUMAN` を使う：
- 人間によるプロダクト／要件の判断
- 外部の認証情報、またはアクセスできないサービス
- ハードウェア、または利用できない外部システム
- 仕様とプラットフォームの矛盾による、スコープの見直し

問題が現在のタスク計画の範囲内でのリポジトリの変更によって修正可能であれば、早まってエスカレーションしてはならない。

## よくある自己正当化

| 自己正当化 | 実際 |
|---|---|
| 「たぶん簡単なパッチで済む」 | パッチ先行のデバッグは手戻りを生む。 |
| 「いくつか修正を試してみよう」 | 複数の修正を当て推量で試すと、根本原因が隠れる。 |
| 「仕様がおそらく間違っているので、こちらで合わせよう」 | 仕様の矛盾は、明示的に表面化させなければならない。 |
| 「ドキュメントの検索は任意だ」 | ランタイム／依存関係の問題では、ドキュメントやバージョン固有の issue に、根本原因への最短経路があることが多い。 |

## 出力形式

```md
## Debug Report
- ROOT_CAUSE: <1〜2 文での根本原因>
- CATEGORY: MISSING_DEPENDENCY | RUNTIME_MISMATCH | MODULE_FORMAT | NATIVE_ABI | CONFIG_GAP | LOGIC_ERROR | TASK_ORDERING_PROBLEM | TASK_DECOMPOSITION_PROBLEM | SPEC_CONFLICT | EXTERNAL_DEPENDENCY
- FIX_PLAN:
  1. <リポジトリ内で修正可能な具体的アクション>
  2. <リポジトリ内で修正可能な具体的アクション>
- VERIFICATION: <修正を確認するためのコマンド>
- NEXT_ACTION: RETRY_TASK | BLOCK_TASK | STOP_FOR_HUMAN
- CONFIDENCE: HIGH | MEDIUM | LOW
- NOTES: <次の実装担当が知っておくべきコンテキスト>
```
