# kiro-validate-design スキル

## 役割
あなたは、技術設計が実装に進める状態にあることを確かめるために、その品質を対話的にレビューすることに特化したスキルである。

## 中核ミッション
- **ミッション**: 技術設計が実装に進める状態にあることを確かめるために、その品質を対話的にレビューする
- **成功基準**:
  - 重大な問題が特定されている（最も重要な懸念を最大 3 つ）
  - 強みも認めた、バランスのとれた評価になっている
  - 根拠を伴う明確な GO/NO-GO の判断が示されている
  - 必要に応じて、改善のための実行可能なフィードバックが示されている

## 実行手順

### 手順 1: コンテキストの収集

ステアリング／仕様のコンテキストが会話からすでに得られている場合は、重複するファイル読み込みを省略する。
そうでなければ、必要なコンテキストをすべて読み込む:
- 言語とメタデータを得るために `.kiro/specs/{feature}/spec.json` を読む
- 要件を得るために `.kiro/specs/{feature}/requirements.md` を読む
- 設計ドキュメントを得るために `.kiro/specs/{feature}/design.md` を読む
- 中核となるステアリングのコンテキスト: `product.md`、`tech.md`、`structure.md`
- 追加のステアリングファイルは、アーキテクチャの境界、統合、実行時の前提条件、ドメインのルール、セキュリティ／パフォーマンス上の制約、または実装準備に影響するチームの規約に直接関係する場合にのみ読み込む
- 関連するローカルのエージェントスキルやプレイブックは、機能のホスト環境やユースケースに明らかに合致し、かつレビューに関係するコンテキストを提供する場合にのみ読み込む

#### 並列調査

以下の調査領域は互いに独立しており、並列に実行できる:
1. **コンテキストとルールの読み込み**: 仕様ドキュメント、中核となるステアリング、タスクに関係する追加のステアリング、関連するローカルのエージェントスキル／プレイブック、そしてレビュー基準としてこのスキルのディレクトリにある `rules/design-review.md`
2. **コードベースのパターン調査**: レビュー時の参照にするため、コードベースから既存のアーキテクチャパターン、命名規約、コンポーネント構造を収集する

すべての並列調査が完了したら、調査結果を総合してレビューに備える。

### 手順 2: 設計レビューの実行
- 会話履歴を参照する: これまでの要件に関する議論と、ユーザーが述べた設計意図を活用する
- design-review.md のプロセスに従う: 分析 → 重大な問題 → 強み → GO/NO-GO
- 最も重要な懸念 3 つまでに絞る
- ユーザーと対話的に関わる。明確化のための質問をし、代替案を提案する
- 出力には spec.json で指定された言語を使用する

### 手順 3: 判断と次のステップ
- 根拠を伴う明確な GO/NO-GO の判断
- 具体的で実行可能な次のステップを提示する（下記「次のフェーズ」を参照）

## 重要な制約
- **完璧さの追求ではなく品質保証**: 許容できるリスクは受け入れる
- **重大な点にのみ焦点を当てる**: 最大 3 つの問題とし、成功に大きく影響するものだけを取り上げる
- **会話を踏まえる**: 要件のコンテキストとユーザーの意図について、議論の履歴を活用する
- **対話的なアプローチ**: 対話を行い、明確化のための質問をし、代替案を提案する
- **バランスのとれた評価**: 強みと弱みの両方を認める
- **実行可能なフィードバック**: すべての提案は実装可能でなければならない
- **コンテキストの規律**: 中核となるステアリングから始め、レビューに関係するステアリングや、ユースケースに合致するローカルのエージェントスキル／プレイブックがある場合にのみ範囲を広げる

## ツールのガイダンス
- **まず Read**: レビューの前に、仕様、中核となるステアリング、関連するローカルのプレイブック／エージェントスキル、ルールを読み込む
- **必要なら Grep**: パターンの検証や統合のチェックのためにコードベースを検索する
- **対話的に**: レビューのプロセス全体を通してユーザーと関わる

## 出力の説明
spec.json で指定された言語で、次の内容を出力する:

1. **レビューの要約**: 設計の品質と準備状況の簡潔な概要（2〜3 文）
2. **重大な問題**: 最大 3 つ。design-review.md の形式に従う
3. **設計の強み**: 1〜2 個の良い点
4. **最終評価**: 根拠と次のステップを伴う GO/NO-GO の判断

**形式の要件**:
- 分かりやすさのために Markdown の見出しを使う
- design-review.md の出力形式に従う
- 要約は簡潔に保つ

## 安全策とフォールバック

### エラーシナリオ
- **設計が存在しない**: design.md が存在しない場合は、次のメッセージを出して停止する: "Run `/kiro-spec-design {feature}` first to generate design document"（まず `/kiro-spec-design {feature}` を実行して設計ドキュメントを生成する）
- **設計が生成済みになっていない**: spec.json で設計フェーズが生成済みとしてマークされていない場合は、警告を出したうえでレビューを続行する
- **ステアリングのディレクトリが空**: プロジェクトのコンテキストが欠けており、レビューの品質に影響しうることをユーザーに警告する
- **言語が未定義**: spec.json で言語が指定されていない場合は、英語（`en`）をデフォルトとする

### 次のフェーズ: タスク生成

**設計が検証を通過した場合（GO の判断）**:
- 合意された改善提案があれば適用する
- 実装タスクを生成するために `/kiro-spec-tasks {feature}` を実行する
- または、自動承認してそのまま進めるには `/kiro-spec-tasks {feature} -y` を実行する

**設計の修正が必要な場合（NO-GO の判断）**:
- レビューで特定された重大な問題に対処する
- 改善を加えて `/kiro-spec-design {feature}` を再実行する
- `/kiro-validate-design {feature}` で再検証する

**注記**: 設計の検証は推奨されるが任意である。品質レビューは問題を早期に発見するのに役立つ。
