# 設計レビューのプロセス

## 目的
技術設計ドキュメントが、許容できるリスクの範囲で実装に進めるだけの堅実さを備えていることを確かめるため、その品質を対話的にレビューする。

## レビューの考え方
- **完璧さの追求ではなく品質保証**
- **重大な点に焦点を当てる**: 最も重要な懸念 3 つまでに絞る
- **対話的なやり取り**: 一方的な評価ではなく、設計者と対話する
- **バランスのとれた評価**: 強みと弱みを認める
- **明確な判断**: 根拠を伴う、確定的な GO/NO-GO

## スコープと対象外

- スコープ: プロジェクトのコンテキストと標準に照らして設計ドキュメントの品質を評価し、GO/NO-GO を判断する。
- 対象外: 実装レベルの設計、深い技術調査、技術選定の確定は行わない。そうした項目は、設計フェーズの繰り返しに委ねる。

## 中核となるレビュー基準

### 1. 既存アーキテクチャとの整合（重大）
- 既存システムの境界とレイヤーへの統合
- 確立されたアーキテクチャパターンとの一貫性
- 適切な依存の方向と結合度の管理
- 現在のモジュール構成との整合

### 2. 設計の一貫性と標準
- プロジェクトの命名規約とコード標準の遵守
- 一貫したエラー処理とロギングの戦略
- 統一された設定管理と依存関係管理
- 確立されたデータモデリングのパターンとの整合

### 3. 拡張性と保守性
- 将来の要件に対する設計の柔軟性
- 関心の明確な分離と単一責任
- テスト容易性とデバッグへの配慮
- 要件に見合った適切な複雑さ

### 4. 型安全性とインターフェース設計
- 適切な型定義とインターフェースの契約
- 安全でないパターンの回避（例: TypeScript での `any`）
- 明確な API の境界とデータ構造
- 入力の検証とエラー処理の網羅

## レビューのプロセス

### 手順 1: 分析する
すべてのレビュー基準に照らして設計を分析し、統合、保守性、複雑さ、要件の充足に影響する重大な問題に焦点を当てる。

### 手順 2: 重大な問題を特定する（3 つ以下）
各問題について:
```
🔴 **Critical Issue [1-3]**: [簡潔なタイトル]
**Concern**: [具体的な問題]
**Impact**: [なぜそれが重要か]
**Suggestion**: [具体的な改善策]
**Traceability**: [requirements.md の要件 ID／セクション]
**Evidence**: [設計ドキュメントのセクション／見出し]
```

### 手順 3: 強みを認める
バランスのとれたフィードバックを保つため、1〜2 個の優れた点を認める。

### 手順 4: GO/NO-GO を判断する
- **GO**: アーキテクチャ上の重大な不整合がなく、要件に対応しており、実装への道筋が明確で、リスクが許容範囲内である
- **NO-GO**: 根本的な衝突、重大な欠落、高い失敗リスク、不釣り合いな複雑さがある

## トレーサビリティと証拠

- 各重大な問題を、`requirements.md` の関連する要件（ID またはセクション）に紐付ける。
- 評価を裏付けるため、設計ドキュメント内の証拠の場所（セクション／見出し、図、または成果物）を示す。
- 該当する場合は、問題の正当性を示すためにステアリングのコンテキストにある制約を参照する。

## 出力形式

### Design Review Summary（設計レビューの要約）
全体的な品質と準備状況について 2〜3 文。

### Critical Issues (≤3)（重大な問題）
それぞれについて: Issue（問題）、Impact（影響）、Recommendation（推奨）、Traceability（トレーサビリティ。例: 1.1, 1.2）、Evidence（証拠。design.md のセクション）。

### Design Strengths（設計の強み）
1〜2 個の良い点。

### Final Assessment（最終評価）
Decision（判断。GO/NO-GO）、Rationale（根拠。1〜2 文）、Next Steps（次のステップ）。

### Interactive Discussion（対話的な議論）
設計者の視点、代替案、明確化、必要な変更について対話する。

## 長さと焦点

- 要約: 2〜3 文
- 各重大な問題: 合計 5〜7 行（Issue/Impact/Recommendation/Traceability/Evidence を含む）
- レビュー全体: 簡潔に保つ（目安は約 400 語）

## レビューのガイドライン

1. **重大な点に焦点を当てる**: 成功に大きく影響する問題のみを指摘する
2. **建設的な口調**: 批判だけでなく解決策を示す
3. **対話的なアプローチ**: 一方的な評価ではなく対話を行う
4. **バランスのとれた評価**: 強みと弱みの両方を認める
5. **明確な判断**: 確定的な GO/NO-GO の推奨を行う
6. **実行可能なフィードバック**: すべての提案が実装可能であることを確かめる

## 最終チェックリスト

- **重大な問題が 3 つ以下**であり、それぞれに Impact と Recommendation が含まれている
- **トレーサビリティ**: 各問題が要件 ID／セクションを参照している
- **証拠**: 各問題が設計ドキュメント内の場所を示している
- **判断**: 明確な根拠と次のステップを伴う GO/NO-GO がある
